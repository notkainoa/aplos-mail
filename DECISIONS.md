# Decisions

## 2026-10-29 — Timer loop: the 1 s backoff applies only to sources that do not move `next()`

- **The F3 contract, not an every-fire cap.** `DeadlineSource.fire`'s contract is "must move `next()` past `now`, or the loop backs off 1 s and logs". `clock/loop.ts` originally also clamped every re-fire to `lastFire + 1 s`, which throttled a correct source that does move its deadline (eng-views' 50 ms ticker registered as `views`) to one fire a second. The per-fire clamp is removed; a stuck source still backs off through `backoffUntil`, and sustained spinning is bounded by the wake budget (`maxWakesPerHour`), which spaces out a source's fires once it exceeds it — the two contract-sanctioned rate limits.
- **The wake budget is per source and counts fires (review, 2026-10-29).** One shared 3,600-an-hour budget throttled eng-views' 20 Hz tick to about 1 Hz after three minutes and let one runaway source delay the outbox by up to an hour. Each source now has its own budget (default 100,000 an hour, above the 72,000 a 50 ms tick needs), counted per fire so a direct fire cannot dodge it, and a source fires at most once per pass so an inching `next()` yields to the event loop.
- **`stop()` waits for a fire in flight** (up to `STOP_GRACE_MS`, 10 s) so `Engine.close` does not close the store under a send mid-fire.
- **A host-injected `deadlines` wins.** `clock/module.ts` provides `services.deadlines` only when it is the `absent()` stand-in. A host or test that injects a registry through `EngineOptions.ports` owns it entirely, including lifecycle — the injected object may be a bare `DeadlineRegistry` with no `start`/`stop`.

## 2026-10-28 — Test mode: only on data made for the run, never in release builds

- **Release builds compile test mode out.** `scripts/build-main.mjs` defines `__APLOS_TEST_MODE__` as false when `APLOS_RELEASE_BUILD=1` (`release:build`, `release:publish`), so a distributed app ignores `APLOS_TEST` and `APLOS_DATA_DIR` and behaves normally, which is what plan 40's `verify-hardening` checks. Local `npm run package` builds and development runs keep test mode, and agents verify packaged behaviour on those (freeze R2H-4).
- **Only a directory made for the run.** With `APLOS_TEST=1`, `APLOS_DATA_DIR` must exist and resolve (symlinks followed) inside the system temp folder or an explicit `APLOS_TEST_ROOT`. It must not be that folder itself, `/`, home, or the real or preview Aplos data folder. A folder that holds a mailbox key without the `.aplos-test` marker is refused. The marker is written on first start, so a restart of the same run works (freeze R2H-1).

## 2026-10-28 — Revamp Phase 0 artifacts F1-F5 and F7 (freeze candidate)

- **zod/mini, types-only in the engine.** The contract's schemas use `zod/mini` (about 35 KB against full zod's 188 KB in a neutral bundle). The engine core imports contract *types* and the zod-free error classes only; transports validate with `parseArgs` at the host boundary (ARCH 9.3; plan 10 section 3's named fallback), because the runtime schemas plus zod cost about 158 KB of the 400,000-byte budget.
- **Engine budget measured without `legacy/`.** The portability test applies the no-Node rule to all of `packages/engine/src`, but the 400,000-byte check counts only the new engine (UTF-8 bytes, unminified) and forbids new code from importing `legacy/`, which Phase 2 deletes.
- **Contract naming.** Every method is `Type/verb` (`Mail/release`, `Mail/toggleQuotes` rather than `Mail/frame.release`), so the typed client is `api.<type>.<verb>`. Binary moves as `Blob/put` then a `blobId`, never base64. Scopes: `read`, `triage`, `draft`, `send`, `ai`, `admin`, `host`. Submissions add `scheduled`. `conflict` is a reply error type, not a governor error class (adapters return conflicts as results). No key characters (`last4`) leave the engine.
- **Ports (F3)** follow the Providers thread's proposal v2 with the changes listed in STATUS.md (one adapter per account, results for conflicts, only proof makes a send not-sent, one placements list, governor-owned token refresh, `reconnectBy` computed by the host), plus every fix from the Providers review (`packages/engine/src/ports.review-answers.md`): connect ignores auth blocks; per-account monotonic sweep generations with `SweepBound.until` and a `sweep` write in the same commit; the overdue rule applies to queued submissions only, and a submission found `sending` at start becomes `uncertain` and runs `findSent` first.
- **Store (F4).** Schema 0001 is ARCH 3.2 plus the Providers review's S1-S11 and the later additions; `store.commit` is synchronous, data-only and idempotent per required `opId`; `seq` moves once per client-visible commit; `changes` is keyed `(seq, type, id)`; rollups are computed in the store, never taken from a batch.
- **Logger (F7).** The catalog is plain data checked at runtime; its zod schemas are used in tests. Addresses are hashed with a salted synchronous SHA-256 (first 16 hex digits); free text is redacted aggressively and anything over 2,000 characters is replaced whole.
- **UI gaps.** Every gap the UI threads sent is answered in `packages/contract/GAPS.md`.

## 2026-10-27 — Revamp Phase 0 step 1: legacy folders and workspaces

- **Moved, not rewritten.** Today's engine is `packages/engine/src/legacy/` (`@aplos/engine`), the five shared files it needs (`types`, `ask`, `mailbox`, `summary`, `live`) are `packages/contract/src/legacy/` (`@aplos/contract`), and today's renderer is `apps/desktop/src/renderer/legacy/`. All three are read-only reference until Phase 2 deletes them (roadmap 1.1, plan 10 E1 item 1).
- **No re-export stubs in `src/shared`.** The plan allowed one-line stubs so importers compile unchanged. The codemod (`scripts/codemod-imports.mjs`) rewrote every importer to `@aplos/contract/legacy/*` instead, so a stub would have no importer, and leaving a file at the old path would stop git from recording the five moves as renames (`git log --follow` would lose their history). `src/shared/version.ts` stays in the app.
- **`@aplos/engine/legacy/*`, not `@aplos/engine/*`.** Imports of legacy code say so (`@aplos/engine/legacy/discover`), so the new engine's own paths stay free and Phase 2 can find every legacy importer with one search.
- **Internal source packages.** Each package's `exports` maps `./legacy/*` to TypeScript source; there is no build step. tsconfig `paths` and a Vite alias resolve the same files. `scripts/build-main.mjs` bundles `@aplos/*` and keeps every third-party package external (esbuild's `packages:'external'` would have left `@aplos/*` out of the app). `@aplos/*` are dev dependencies of `@aplos/desktop`, so electron-builder never copies their source into `app.asar`; third-party packages they use (today `fast-xml-parser`) stay declared in `apps/desktop/package.json` too, because that is the manifest electron-builder reads.
- **Provider types in the contract.** `AccountPreset`, `ProviderCapabilities`, `ProviderKind` and `ServerSettings` moved to `packages/contract/src/legacy/provider-types.ts`; the engine's `provider.ts` re-exports them. The contract never imports the engine.
- **`appVersion` through `EngineOptions`.** The engine no longer reads the app's `package.json`; the host (`src/main/service.ts`) passes it.
- **Portability test.** It moved to `packages/engine/tests/`, bundles every `.ts` file under `src/` at any depth (instead of one entry file, which nothing provides yet), and has a negative test that plants a `node:fs` import two folders deep. The orchestration run with the Node store, staged memory and Groq stays in the app as `tests/engine-host.test.ts`.
- **Engine size, measured.** The neutral bundle of everything under `packages/engine/src` (all legacy today) is about 353,500 characters unminified (the test's measure; path comments move it by a few hundred) and 201,361 bytes minified, the same as before the move, against the 400,000 budget. MOBILE.md's 146,544 minified figure is from when the engine had 11 modules. The freeze review should decide whether the budget applies to the new engine entry without `legacy/` (which Phase 2 deletes), because legacy plus zod plus new code would not fit.
- **Packaged-app proof without a window.** `scripts/verify-release.mjs` shows the app's window, which the headless rule forbids, so step 1 was proved by `npm run package` plus a content check of `app.asar` instead. The full run waits for F8's hidden test mode (`APLOS_TEST=1`).

## 2026-10-24 — OAuth clients built into releases

- **Closes the open decision on where OAuth client config lives for a public release.** The v0.2.0 draft, installed on a second Mac, could not connect Google: a packaged app read only `~/.config/aplos-mail/.env`, which exists only on the owner's machine.
- **Embedded at build time from repository secrets.** Google's "Desktop app" client type treats the client secret as non-confidential (an installed app cannot keep a secret; Google documents this, and PKCE plus the loopback redirect protect the flow), so bundling it is the standard approach for desktop mail clients. Microsoft's public client has no secret at all. Alternatives rejected: asking each user to create a Cloud project (not workable for a download), and a hosted token-exchange server (an online dependency and a service to run, for no real secrecy gain).
- **How.** `scripts/oauth-defines.mjs` gives esbuild `define` values for `src/main/oauth-config.ts`: the Google client ID and secret and `MICROSOFT_CLIENT_ID`, read from the build environment only when `APLOS_RELEASE_BUILD=1` (`release:build` / `release:publish`). Every other build, `tsx` and the tests inline nothing. Values live only in `dist/main/engine.cjs` in the asar, never in a tracked file or `package.json`; a test checks the repo tree after a placeholder build.
- **Precedence: environment, then built-in, then none.** An ID in `process.env` (dev `.env` or `~/.config/aplos-mail/.env`) wins together with its own secret, so the owner can test another client; the built-in pair is never mixed with an env value. Explicit adapter options (tests, emulator) still win over both.
- **Messages.** Without a client: "Google sign-in isn't available in this build." (Outlook likewise). Development builds add the `.env` hint; release builds don't. The renderer shows the engine's message (`capabilities.get` gained `googleUnavailable` / `microsoftUnavailable`) instead of its own hardcoded copy.
- **Release guard.** On CI a release build without the Google pair fails, unless `APLOS_ALLOW_NO_GOOGLE=1`. Local release builds warn. `MICROSOFT_CLIENT_ID` is optional until Outlook ships.
- **Still open.** Google verification for the restricted Gmail scopes. Until the consent screen is verified, only listed test users can finish sign-in, and Google shows its unverified-app warning.

## 2026-10-23 — Release pipeline and auto-update

- **Artifacts.** electron-builder builds a DMG (what people download) and a ZIP (what electron-updater needs on macOS) for arm64 and x64, plus `latest-mac.yml`. Names have no spaces (`Aplos-Mail-X.Y.Z-arch.ext`), because GitHub rewrites spaces in asset names and the feed would point at files that do not exist. `npm run package` stays the fast this-Mac `dir` build; `npm run release:build` makes the full set. The asar, `extraResources` bin and `extendInfo` are unchanged.
- **Signing.** Hardened runtime with `build/entitlements.mac.plist` (allow-jit, allow-unsigned-executable-memory, disable-library-validation, audio-input), also used for helpers. The Swift symbol helper is now built universal (`lipo` of arm64 and x86_64 slices, macOS 12 minimum) so the Intel build is not shipping an arm64-only binary. It needs no `binaries` entry: electron-builder's signing pass walks the whole bundle, and the test build showed `Contents/Resources/bin/aplos-symbols` signed with the runtime flag like the app.
- **No certificate yet → ad-hoc, not unsigned.** `scripts/release-build.mjs` signs only when `CSC_LINK` (CI) or `CSC_NAME` (local) is set, and otherwise sets `CSC_IDENTITY_AUTO_DISCOVERY=false`, `mac.identity=-` and `notarize=false`. Ad-hoc signing goes a little further than "skip signing": an Apple Silicon app whose seal is broken (Info.plist edited after Electron's own ad-hoc signature) is reported as "damaged" after download, while an ad-hoc app can be opened with Open Anyway. Notarization uses electron-builder's built-in `notarize` with `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID`; a partial set fails the build. Empty GitHub secrets are treated as absent.
- **Updater.** `electron-updater`, GitHub provider (notkainoa/aplos-mail), drafts publish as `releaseType: draft`. `src/main/updates.ts` holds the state machine (idle, checking, current, downloading, ready, error, disabled) with no Electron import, so it is tested with a fake updater. It checks 60 s after launch and every 6 h, downloads silently, and never installs on its own: `autoInstallOnAppQuit` is off, so even quitting does not swap the app. Restart runs the normal quit (drafts saved, engine closed) and only then calls `quitAndInstall`; if the owner cancels a draft prompt, the restart is cancelled too. Later hides the notice for that version until a manual check (menu or Settings) or next launch; the download stays cached.
- **When updates are off.** Development (unless `APLOS_UPDATE_DEV=1` with `dev-app-update.yml`), the browser preview, running from a mounted DMG or App Translocation, and any bundle without a Developer ID Team ID (read with `codesign --display`). Squirrel.Mac only installs an update signed by the same team as the running app, so unsigned and ad-hoc builds would fail at the swap; they say so in Settings → General and in the log instead. electron-updater is loaded only when updates can run.
- **Notice.** A persistent toast ("Aplos X.Y.Z is ready" · Restart · Later) on the existing toast axis. Toasts gained `persistent`, `key` and a quieter `secondary` action; persistent toasts keep their action when newer Undo toasts arrive. Only the main window shows it. No new icon.
- **Version.** One source: `apps/desktop/package.json`, imported through `src/shared/version.ts` (inlined by Vite and esbuild) instead of three hardcoded `0.1.0`s. The root package.json now carries the same version; `scripts/release.mjs` bumps both plus the lockfile, commits, tags and prints the push command. It never pushes.
- **CI.** `ci.yml` uses a `dorny/paths-filter` job so desktop jobs (macOS: typecheck, test, build) run for `apps/desktop/**`, `scripts/**` and shared root files, the website job (Ubuntu: typecheck, build) for `apps/web/**`, and both for root `package*.json`, `packages/**` and the workflow itself. Skipped jobs count as passing for branch protection. `release.yml` runs on `v*` tags, checks the tag matches the app version, tests, then `electron-builder --publish always`. Node 24 to match local development.
- **Google/Microsoft client IDs were runtime-only at first.** Superseded on 2026-10-24: release builds now carry the clients (see "OAuth clients built into releases").
## 2026-10-23 — AI keys in Settings and first-run setup (M40)

- **Where keys live.** Keys typed in Settings → AI go into `ai-keys.enc.json`, a vault file sealed per entry with the same keychain-protected data key (`engine-key.bin`, Electron safeStorage) as account credentials. They are never in app state, `state.json`, SQLite or logs. The engine only ever hands the renderer `{source:'saved'|'environment', last4}`, and `last4` only for keys of 12 characters or more.
- **Precedence: saved, then environment, then none.** A small resolver (`src/main/ai-keys.ts`) is passed to every provider as `apiKey:()=>keys.resolve(id)`; providers read it per request (`readKey` in `llm.ts`), so saving or removing a key works without a restart and `available` is now a getter. Without a resolver, providers still read their environment variable, so `.env`, the eval scripts and `verify-release --live-ai` are unchanged. Claude keeps one SDK client per key.
- **Paste never passes through the renderer.** In the desktop app, Paste is a main-process method (`ai.key.paste`) that reads the clipboard and forwards it straight to the engine's `ai.key.set`. Typing a key into the masked field does pass through the renderer once, at entry; the field is cleared as soon as it saves.
- **Test shows the provider's own words.** `ai.key.test` makes one cheap request: the model list for Groq, OpenAI, Gemini, Claude (one page), Ollama, LM Studio and a custom server; OpenRouter's `/key` (its model list is public); one 1-token completion for OpenCode Go (its model list also needs no key). Unlike every other AI error, a refused key shows the provider's `error.message`, with the key and anything key-shaped redacted, because that is what the owner needs to fix it. Saving runs the test automatically.
- **Errors point at Settings, not `.env`.** "Add your Groq key in Settings → AI to use Groq." and "… rejected the API key. Check it in Settings → AI." The summary card's explanations follow.
- **Browser preview.** No safeStorage there, so the store reports `secure:false` and every key field says keys can only be saved in the desktop app, naming the environment variable to use instead. Saving is refused by the engine with the same message.
- **OAuth client config stays build/environment-time.** `GOOGLE_CLIENT_ID`/`SECRET` and `MICROSOFT_CLIENT_ID` are not user-entered.
- **Welcome flow.** Replaces the single welcome card. Steps: Welcome (Add an account / Look around with demo mail) → the existing add-account dialog → AI (Groq preselected, a provider menu for the keyed providers, the same key field as Settings, a "Get a key" link, Skip for now) → Microphone (hold A / hold Space explained; Allow now via `systemPreferences.askForMediaAccess`, or Later; the status is read with `getMediaAccessStatus` so opening the step never prompts) → Done (Space, A, J K, ?). It runs once per data folder (`settings.onboardingDone`, already persisted) and reopens from Settings → Help & about → Show welcome. The App decides once per load whether to open it, so connecting an account (which the engine already marks as onboarded) doesn't cut the flow short.
- **Escape skips the current step**, and on the first step skips setup; the footer says which. The welcome stays mounted (hidden) under the add-account dialog so focus returns to it instead of the page underneath.
- **Choosing another provider in the welcome.** If the owner saves a key for, say, Claude while Groq has no key, Ask, Summaries, Drafts and Plans that still point at Groq move to that provider's first curated model (and Voice to OpenAI's when it's ChatGPT). Otherwise the defaults stay on Groq.
- **No AI glyph.** The AI step uses a key icon; no sparkle, wand or stars anywhere.

## 2026-10-15 — Multi-provider, serverless architecture

- Researched two open-source mail backends (Redakt, Superlocal) for patterns only; no code copied. Adopted: incremental provider sync from a stored cursor, a per-account rate gate, durable local operations with undo, a send hold that cannot double-send, content-hash AI caching, paged queries with change events. Rejected for Aplos: a hosted Postgres/web backend, multi-user tenancy and running our own mail server (Redakt's Stalwart approach): the user's mail host is the sync server.
- Target shape: one platform-free TypeScript engine (`src/engine`) shared by desktop now and a React Native app later; platform specifics enter through small ports (SQL database, secure storage, sockets, OAuth, background scheduling). Providers implement one contract: `sync(cursor)` returning changed threads, flag-only updates, removals and the next cursor; `apply`; `send`; `fetchBody/attachment`; capabilities. Planned adapters: Gmail API, Microsoft Graph (MSAL public client, delta per folder), JMAP (Fastmail), IMAP+SMTP (iCloud, Yahoo, AOL, generic; own threading from Message-ID/References). Proton only through Bridge on desktop. TypeScript over a Rust core because all current and planned runtimes run TypeScript; raw IMAP sockets on mobile stay behind a port.
- Storage is SQLite through Node's built-in `node:sqlite` (Node 24 and Electron 44 both ship SQLite 3.5x with FTS5), so no native module rebuild is needed for Electron. The engine owns a minimal synchronous SQL port so mobile can use op-sqlite/expo-sqlite later. The existing `state.json` is imported once and kept as `state.json.imported`.
- Aplos-only workflow state (Done vs. merely read, Later, todos, due dates, reminders) is kept locally and survives syncs; the host's labels/folders are authoritative for read, star, trash, spam and inbox membership. A thread returns to Home when a new message arrives, when Gmail moves it back to the inbox while the matching Done/Later action is "archive", or when it lands in Trash/Spam. Cross-device sync of the workflow log goes later through an encrypted hidden mailbox folder (no Aplos server).
- Gmail: the first sync fetches the newest 500 threads instead of the whole mailbox; afterwards `history.list` from the stored `historyId` drives sync. Threads that only changed labels are refreshed with `format=minimal`; added messages trigger a full thread fetch; a missing thread is removed locally; an expired cursor (404) falls back to a fresh bounded sync. Older mail is reached through Gmail search, which is limited to 100 threads per query.
- Background sync runs every 60 s and when a window gains focus, behind a per-account gate (single flight, at least 15 s between automatic syncs, exponential backoff after failures up to 15 min). "Sync now" bypasses the interval but not the single-flight rule.
- Triage is local-first. Each change is applied at once and written, in the same transaction, to an `ops` table as a provider change (remote ID, the status it started from, the patch). A worker sends ops in order per account; one failure holds back only that account's later ops, so a thread never gets an older change after a newer one. Failures retry after 30 s doubling to 15 min; "Sync now" retries at once. A 404 drops the op, since the thread is gone. Sync sends ops before pulling, and threads with an op still queued keep their local status, read, star and labels (new arrivals and removals still apply). Undo and reminders go through the same queue. Disconnecting an account drops its ops.
- Sending can never double-send. Each draft gets one Message-ID on the sender's domain when it is first sent, kept across retries. Before calling Gmail, the draft is marked with `sendAttemptAt`. A network error or 5xx is uncertain: Aplos looks for the Message-ID in Sent mail (`rfc822msgid:`) and treats a match as sent; otherwise the draft keeps an error asking the user to check Sent mail. A definite rejection (4xx) is reported as is. After a crash, drafts with `sendAttemptAt` are settled only from Sent mail and never sent again automatically.
- Live push needs a server for Gmail and Graph, so desktop polls. A later optional push relay may store only push token ↔ mailbox ID, never tokens or content. Google restricted scopes need verification; the CASA assessment applies when data passes through a third-party server, so any relay or AI proxy must be checked with Google first. Groq on mobile needs a user-entered key or a proxy; desktop keeps reading `GROQ_API_KEY` from the backend environment.

## 2026-10-16 — M29 workflow sync between devices

- What syncs: each thread's workflow fields (Done/Later/New, reply status, due date, todo, reminder and whether it fired, hidden from Home). Trash and Spam are host state and are not part of it. The log is last-writer-wins per thread (`src/engine/workflow.ts`, platform-free); a merge is commutative, associative and idempotent. Entries are keyed by the host's thread ID (Gmail, Graph, JMAP), or by the thread's root Message-ID for IMAP, whose thread IDs are built per device.
- Only real user edits enter the log (triage, undo, Home hide, fired reminders). Each edit is recorded at edit time as a snapshot of the thread's workflow fields with its edit time and a generation number, in the same transaction as the edit; that edit time, not the sync time, decides conflicts. Mail sync changes (a host archive becoming Done) do not count, or they would override another device's Later. The first device to turn sync on seeds the log from its existing Later, todos, due dates and reminders (timestamped with the thread's last message, so real edits win); a device that joins takes the shared log as it is. Each device remembers which winning entry it applied per thread, so an entry applies once, and an entry for a thread downloaded later (through search, say) still applies when it arrives. A newer message from someone else keeps the thread on Home even if another device marked it Done.
- A round reads every stored copy, merges all of them with this device's edits, writes one new copy and then removes only the copies it read. Two devices writing at once therefore never delete each other's copy; the next round folds both. An edit made while a round is in flight is not acknowledged and its thread is not patched by that round. What a round remembers is saved together with the patches it applies, so a crash in between redoes the round.
- Compaction drops plain entries older than 180 days and records a floor; a merged entry older than another log's floor is rejected, so a long-offline device cannot bring back a Later that was cleared and compacted away.
- Storage: small marked messages in a hidden "Aplos Mail Data" folder per account (a name the user is unlikely to have; a user folder named "Aplos" is ordinary mail). Only messages carrying Aplos's own marker count as records (a header for Gmail and IMAP, a named extended property for Graph, a keyword for JMAP), so user mail is never read or deleted even if it sits in that folder. Gmail uses a label with list and message visibility hidden, `messages.insert`, and trashes replaced copies, because `gmail.modify` cannot delete. Graph uses a hidden folder; IMAP an unsubscribed folder; JMAP an unsubscribed mailbox without a role. Normal sync and search never surface it.
- Encryption: a 28-symbol sync code (130 random bits plus a 2-symbol check, Crockford base32, entered in any case and spacing) → scrypt (N=2^15, random salt per write) → AES-256-GCM with the header authenticated; a separate check value tells a wrong code from damaged data. The code is kept in the credential vault (`workflow-sync.enc.json`), never in app state. Data sealed with a different code or a newer format is reported and never overwritten; damaged data is replaced; a copy too large to open is kept, never replaced, and writes trim old entries until the log fits.
- When: after each account's mail sync, at most every 5 minutes for automatic syncs unless there are edits to share, and on every manual sync. Writes happen only when the merged log differs from the host's copy. Patches from other devices change local state only; the other device already told the host about its own archive or move.

## 2026-10-29 eng-time: the timer loop survives a hung source and a sleeping Mac (Integrator review of #89)

- **A hung `fire` or `next` no longer stalls the loop.** Each call is raced against `clock.sleep`: `FIRE_TIMEOUT_MS` 30 s for `fire`, `NEXT_TIMEOUT_MS` 5 s for `next` (a read is a local query). On timeout the loop logs `engine.watchdog` with `kind: 'timer_drift'` (the catalog has no dedicated timer-stall event; this is the nearest, and `lagMs` carries the timeout), backs the slot off 1 s and carries on with the other sources, so one stuck network call in `sync:*`, ops, drafts or jobs cannot hold back the outbox deadline.
- **A slot never runs concurrently with itself.** An abandoned call leaves the slot `inflight`; `earliest()` and the read step skip it. When the real promise settles (resolve or reject, both handled, so no unhandled rejection) the slot is marked dirty and the loop kicked, which re-reads its deadline. `stop()` is unchanged (10 s grace).
- **The system clock caps every wait at 60 s (`MAX_SYSTEM_WAIT_MS`).** libuv timers use the monotonic clock, which pauses while the Mac sleeps, so an 8 h deadline with 7 h of sleep fired about 7 h late and the send-later rule (suspend a send more than 5 min past `not_before`) could suspend a message due just before wake. `systemTimer` re-checks `Date.now()` every minute (it already re-arms when early), and `sleep` goes through the same timer, so lateness is bounded to about a minute with no host help. The cost is one timer turn a minute while something is armed. The fake clock is unchanged.
- **`Engine.wake()` is added (additive).** It forwards the host's power-resume, network-return or clock-change hook to the loop's `wake()` (a no-op after `close`, or with a host-injected registry that has no `wake`). The host (eng-host) should call it on `powerMonitor` `resume`; with the cap it is an improvement from about a minute to immediate, not a requirement.
- **Small fixes in the same change.** A source marked dirty while another fires is re-read instead of fired on its stale deadline. The 1 s backoff is set before the `timer_drift` log line and every loop log call is wrapped, so a throwing log port cannot cause an immediate re-fire. `register()` with an id already registered still replaces the first source; the replaced slot is orphaned (its running fire is not read again and the new source can overlap it), now documented on `register`.
- **Note for time-2 (outbox): send-level idempotency.** `STOP_GRACE_MS` (10 s) lets a send that outlives it be abandoned at quit, so the same message may be sent again at the next launch. The loop cannot prevent that. The outbox must make a send idempotent (a per-message send key checked before the provider call and recorded in the same commit as the sent state) so a re-fire after an abandoned send is harmless; the same holds for a send abandoned by `FIRE_TIMEOUT_MS`, which keeps running in the background.

## eng-time time-2: the submission state machine (2026-10-29)

- **No new store columns.** The WIP's `0002_outbox` migration collided with the store's own 0002 and 0003 and the store is not this lane's file, so it is dropped. Everything the outbox needs beyond 0001 and `submissions.revision` (when it was queued, the store rev, the `findSent` check count and next check, the sent time, subject and recipient names, the envelope, the `Submission/set` opId) lives as one JSON object in `submissions.error`, next to the problem; `error_until` stays the problem's `until`. `outbox/store.ts` is the only reader and writer, so a later migration that gives these real columns is mechanical. Request to eng-store, not blocking: a partial index on `(state) WHERE state IN ('sending','uncertain')` (the outbox reads those rows on every recompute).
- **The start rule runs on every fire, not only at launch or wake.** A `sending` row that this engine instance is not awaiting (`inflight`) is a lost outcome: it becomes `uncertain` with a `findSent` due now, never `suspended`, re-queued or re-sent. Doing it on every fire needs no wake signal (the loop's `wake()` re-reads `next()`, and `next()` reports a lost row as due now), and it also recovers a row whose settle commit failed in this process. `module.wake()` and `module.start()` remain. Two live engines on one store would let the second turn the first's in-flight send `uncertain`; it still never sends it, the first still settles it `sent`, and the single-instance lock is the real guard.
- **Nothing that can fail runs between the marker and `send`.** The payload (draft read, remote-draft precondition) is built before the marker, and `inflight` is set before it. A send that is never re-sent needs exactly one rule: state `sending` is committed (compare-and-set on the waiting state and `not_before`) before the first byte, and nothing but a human (`sendAnyway`) moves `uncertain` or `failed` back to `queued`.
- **`SendPort.admission` refusing with `send_limit` fails the waiting row** (`failed`, problem with `until`) instead of waiting, the same outcome as a `PausedError` with `cls:'send_limit'` from `send`: never auto-retried (D7), Retry is the user's. Any other refusal waits until its `until` (or polls every 30 s) and stays under the overdue rule.
- **A hung send does not stop the overdue rule.** The account is busy while its job runs, but `next()` still returns `not_before + grace + 1` for its waiting rows, so they are suspended on time ("Send now or Reschedule") instead of waiting silently behind a send that never returns. `SendPort.send` has no abort signal, so adapters must bound their own calls.
- **`findSent` that throws counts as a check that found nothing**, so the owner gets the prompt after the second check even when offline. At launch every `uncertain` row without a due check gets one more round (the Sent folder or the search index may have caught up). `since` is `min(attempt_at, now)`, so a wall clock set back after the marker cannot push the search window past the message.
- **The same revision is never sent twice under a new Message-ID.** `create` refuses a draft whose revision already has a `sent` submission (`stateMismatch`, "already sent"). `sendAnyway` is the one deliberate second delivery of one Message-ID, and only after the prompt; the counting fake's "never two deliveries" invariant excludes it by design.
- **Backward clock jump:** `not_before` is absolute, so a row queued before a jump back waits the difference; nothing sends early and nothing is lost. Forward: waiting rows more than 5 minutes late are suspended, a `sending` row never.
- **The send is built once.** `buildMime` runs at `send` with a random boundary and the bytes are stored in `submissions.mime`; a retry, `sendAnyway` or a restart reuses them byte for byte and the Message-ID is never regenerated. `Message-ID` is `<128 random bits@sender-domain>` (not `aplos.local`), which spam filters prefer.
- **MIME hardening (defects in the WIP).** The SMTP envelope (including Bcc, which was never validated) goes through the same `checkAddress` as the headers, so a CR/LF or a command in an address is refused before anything is queued; non-ASCII domains become punycode, a non-ASCII local part is refused (no SMTPUTF8). `htmlToText` was quadratic on `<`/`<li ` input (a 1 MB draft could hang the engine) and mis-indexed after `toLowerCase`; it is now one linear `indexOf` pass with ASCII lower-casing, and a lone `<` is text. Inline images with a Content-ID go in `multipart/related` so `cid:` resolves. Encoded words are 36 bytes so a folded header stays near 76 columns.
- **`alsoDone` is not handled here** (it needs views' `Thread/act` and op journal), and the outbox does not delete the local draft or its remote copy when a submission is `sent` (time-3's `Draft/*`). `Draft/set|resolve|destroy` must refuse while `liveSubmissionOf(draftId)` exists and call `Submission/set undo` before a destroy.

## eng-time time-2: fixes after the Opus review of the send state machine (2026-10-29)

- **`sendAnyway` waits for the checks.** It is refused unless `checkAt` is absent and the problem is `send.uncertain` (the prompt is showing), with "We are still checking whether this was sent". The same demand (`ifChecksDone`) is part of the commit's compare-and-set, so a check scheduled between the act's read and its commit makes `sendAnyway` lose. Before, a send that reached the server while the search index lagged could be re-sent a second after it went `uncertain`.
- **One `now` per fire.** `fireOutbox` passes its `now` to the start rule, so a recovered row's `checkAt` is never later than the `now` `startChecks` filters with. On a real clock the recovered row's `findSent` now always runs before any other send of the account.
- **Header hardening.** `htmlToText` trims line ends right to left (it was quadratic on long runs of spaces or `&nbsp;`). A Message-ID taken from inbound mail (In-Reply-To, References) must be `<` + printable ASCII except `<>"\` + `>`; anything else is dropped, never thrown. A long attachment name is written as RFC 2231 sections (`name*0=`, `filename*0*=UTF-8''`), a display name or subject word longer than 64 characters is RFC 2047 encoded, a Content-ID over 255 characters is not written, and `buildMime` throws `MimeError` rather than emit a header line over 998 octets.
- **A failed-without-bytes row says Cancel.** `send.noBytes` rows are only ever cleared by Cancel (Retry would fail again, and `send` refuses while the row is live). The copy now says "Cancel it, then open the draft and send it again", and Retry on such a row is refused with that sentence. No new send path: nothing was sent, so Cancel then `send` (new Message-ID) is already safe.
- **`settleFailed` from `uncertain` is intended.** A `NotSentError` for the attempt in flight (same `attempt_at`) proves the bytes did not leave, so it settles `failed` (Retry) even if another engine's start rule had made the row `uncertain`. Pinned by a test.
- **`cancel` of an `uncertain` row waits for the checks too.** It needs the same `ifChecksDone` guard as `sendAnyway` (checks over, problem `send.uncertain`), enforced inside the commit; while a check is pending it is refused with "We are still checking whether this message went out." Cancelling earlier unlocked the draft, a second send got a new Message-ID, and the pending `findSent` result for the first (now `cancelled`) row was dropped: two deliveries. A new `send` for the draft is already refused while any live row (`uncertain` included) exists, checked inside the create commit.
- **Mime limits, round two.** `htmlToText` tracks `atLineStart` instead of reading `out.endsWith` (which flattened the string per tag). `headerSafe` collapses any run of CR, LF, NUL, spaces and tabs to one space, and `foldHeader` folds by index and never emits a whitespace-only line. `References` keeps the first id and the last 20; the top header block may not pass 10,000 octets (`MimeError`, after trimming).

### Gaps for other lanes (found by the review, not fixable in the outbox)

- **eng-contract / eng-host: services.** The production module has no `blobs` or `settings` services (`EngineServices` lacks them): attachments are refused in the real engine ("no longer available") and `undoSendSeconds` is fixed at 10 s until the host provides them.
- **Providers: Bcc on the wire.** The outbox keeps Bcc out of the MIME and puts it in `SubmissionPayload.envelope.rcpt`. An adapter whose API reads recipients from the MIME headers (Gmail `messages.send` raw) must add the Bcc recipients itself (for Gmail, a transient Bcc header on the bytes it uploads, never stored), or Bcc recipients get nothing.
- **Adapters / governor: a hung `SendPort.send` has no engine-side limit.** There is no abort signal; the account stays busy until the adapter returns. Adapters or the governor must bound every send call (the overdue rule still suspends the waiting rows behind it).
- **eng-store: account removal.** Removing an account cascades and silently deletes its queued, scheduled, suspended, failed and uncertain submissions. The store should refuse the removal, or the host should confirm and list what would be lost, before it runs.

## 2026-10-30 — eng-contract: `Draft.incomplete`, the answer to eng-time's request

## prov-gmail-write: the Gmail send transport (2026-10-30)

- **Bcc is the one header the adapter adds.** The outbox never writes Bcc into a sent message (the envelope carries it), but Gmail's API has no envelope: it reads recipients from To, Cc and Bcc and removes Bcc from delivered copies. `send.ts` therefore inserts one folded `Bcc:` line, just before the blank line, for envelope recipients the headers do not name; every other byte is the pinned MIME. A To or Cc address the envelope does not hold is refused, never sent.
- **Header safety is an allow-list, not a fix-up.** The top header block may hold only what the outbox writer emits (Date, From, To, Cc, Subject, Message-ID, In-Reply-To, References, MIME-Version, Content-Type, Content-Transfer-Encoding), each at most once, CRLF only, no control bytes; From must be exactly the account; Message-ID must equal `internetId` (or `findSent` could never settle it). Anything else is `NotSentError` (`permanent`) with no request. A header the engine starts writing must be added to `PINNED_HEADERS` on purpose.
- **`drafts.send` carries the pinned bytes as its media** (upload endpoint, as Google's drafts guide allows), so a phone edit landing between the `drafts.get` precondition and the send cannot be what leaves. Needs confirming on the live gate.
- **A remote draft that is gone (404) is never "failed".** Before sending the pinned MIME instead, the adapter searches Sent for the Message-ID; a hit resolves the send with that copy's ids (an earlier attempt or another device already sent it), so no second copy goes. A `drafts.send` 404 after a successful read is uncertain (the draft may have just been sent elsewhere), settled by `findSent`.
- **Proof rules.** Not sent: anything before the sending request is written (draft read, resumable session open, even a dropped connection there), a refused connection, and only a 400, 401, 403, 413, 429 or a `messages.send` 404 answer. Uncertain: everything after the request was written (5xx, reset, timeout, abort; 408, 409, 499, a `drafts.send` 404 and any other status). A 2xx is accepted mail only when its body is Gmail's Message with a string `id`; any other 2xx is uncertain and `findSent` settles it. A send times out after 60 s plus 1 s per 50 KB so it cannot hold the account's one slot forever.
- **`findSent`** queries `rfc822msgid:<id> in:sent -in:drafts after:<since minus three days>` with spam and trash included, then re-reads each hit's labels and Message-ID: found only for SENT without DRAFT. A failed search, a hit that vanished before it was read, or a second page is thrown, never `absent`.
- **Review follow-up (supersedes the bullets above where they differ).** `drafts.send` is OFF by default (`GoogleProviderOptions.useDraftsSend`): every send is the pinned MIME through `messages.send` and the engine removes the remote draft itself. ## prov-gov: the lease's follow-ups after #127 (2026-10-30)

## 2026-10-30 — eng-contract/eng-time: BINDING (4) inline parts and `cid:` make a copy incomplete

- **A remote draft copy with an inline part is not complete.** Inline parts (a pasted image) are not delivered, and `hasAttachments` of a message counts only visible attachments, so a clean draft whose phone copy brought a `cid:` image was replaced by a body with a broken reference, dropping this device's own inline image. ## 2026-10-31 — eng-contract/eng-time: BINDING (c) a copy is adopted only when proven ours

The running upload's fingerprint is in `uploading`.
- **Two rows never share a remote draft (Opus review of this change).** History may show an unproven copy as a remote draft before the upload's reply arrives. The reply (`synced`) then names that remote draft: the early row is the same copy, and is dropped, ONLY when it is untouched (`origin: 'remote'`), holds the very message id the reply names, and has no send queued (`sameCopy`). Any other early row (a newer, phone-edited version; a draft the owner edited or is discarding; one with a send in its undo window) is kept and this draft is NOT bound to it: the upload is treated as done (`wrote` and `prints`, NOT `earlier`: the next create must not point back at the copy the other row holds, or an adapter would replace it and loop), `dueAt` stays so the next upload makes its own copy, a discarded draft just ends. A create-path conflict (`adoptedByConflict`) likewise refuses to bind to a copy another row already shows. Nothing is lost either way: the other row keeps the phone's content in front of the owner. The cost is a visible duplicate, as decided.

## 2026-10-30 — prov-gmail: PORT GAP 2 closed on the Gmail side (`DraftUpload.supersedes`)

- **Rule.** A create whose own Message-ID finds nothing looks up each Message-ID in `supersedes` (at most the last five, never its own, only searchable ones): the drafts search per id, the newest drafts once, then all mail. A draft found is REPLACED (`drafts.update`; the result names its `remoteDraftId`, new message id) only when all hold: still a DRAFT (not SENT or TRASH) with the message id the search showed; its raw Message-ID header is one of `supersedes`; its thread is the upload's `remoteThreadId` when that is set; and its raw bytes canonicalise (`draft-compare.ts`, boundaries blanked, line endings normalised) to an upload this adapter recorded for the same local draft under that same Message-ID (`DraftAttempts`, SHA-256 of the canonical form, last five per draft, 100 drafts). The record is made BEFORE every create or replace request goes out, so a reply lost after the copy landed still leaves the proof.
- **Otherwise nothing is written.** A phone edit of the earlier copy (even one that keeps our Message-ID), a copy of another local draft, a Gmail rewrite, or no record: `{kind:'conflict'}` with `remoteDraftId`, `remoteMessageId`, `remoteInternetId` (as for gap 4). A SENT or TRASH message holding a listed Message-ID (no draft found): `{kind:'gone'}` as today, never recreated. A DRAFT-only hit the lookups missed: thrown as index lag. A draft with any other Message-ID is never read as ours. The adapter deletes nothing. Absent or empty `supersedes`: today's lookups, unchanged.
- **Deviation from the spec text: in-process memory, not `provider_memory`.** `saveDraft` returns only a `DraftSaveResult`; `provider_memory` is written through a sync step's result, and `ctx.memory` is read-only, so the adapter cannot persist the hashes from a save. The record lives in a per-adapter `WeakMap` keyed by the deps object. After a restart nothing is provable, so the create answers `conflict` (the owner's "keep mine" recovers) and never replaces. Safe, but an uncertain create that spans an app restart still ends in a conflict instead of a replace. Closing that needs a persistence channel on the draft port (an additive `memory` write on `DraftSaveResult`, or a store handle on `AdapterContext`), an eng-contract change; not requested here.
- **Costs.** Each listed id adds one search (5) and 20 per hit read; a replace adds one raw read (60) and an update (15). The replace has the same millisecond window as any update (Gmail has no etag), and the governor may re-send an `idempotentWrite` update after a transient failure.
- **Still true.** A second earlier copy beyond the one replaced (two earlier creates both landed) stays as a duplicate the owner removes; nothing deletes it. The caveat "an uncertain create followed by an edit can leave two remote copies" is removed for the normal case. TODO(live): Gmail rewriting headers or wrapping of an uploaded draft would show our own copy as a conflict (safe).

## 2026-10-31 eng-contract: `ListHeaders.authenticated` gates List-Unsubscribe one-click (RFC 8058 section 4)

## 2026-10-31 eng-html html-3: the mail sanitizer (`packages/mail-html`, `MailHtml` port)

- **Design.** `mailHtml: MailHtml` (`version: 'mail-html/1'`, pure, synchronous, no DOM or Node imports; a test reads every `src/` import) in `packages/mail-html/src`: `parse.ts` builds a tree over htmlparser2 12's exported `Tokenizer`; `sanitize.ts` walks it iteratively (a stack of frames, depth cap 256) and writes a fresh document from the allowlist in `policy.ts`, every text and attribute value escaped (`escape.ts`); `css.ts` re-tokenizes `<style>` and `style=""` with `@csstools/css-tokenizer` and writes them back token by token. Nothing is copied from the input as markup, so the parser's view of hostile input only affects which text survives, never what the output means; the browser's reading of the output is checked by a parse5 oracle (`tests/oracle.ts`). The earlier unreviewed branch (`rv/eng-html/sanitizer`, `wip-pause-1028`) was read line by line; its allowlist, CSS writer and image book were kept and corrected, the rest rewritten.
- **Why not htmlparser2's `Parser`.** Measured: 100,000 nested `<div>`s take 4.4 s to parse (8.8 s to render with the earlier branch), because its open-element stack uses `unshift`/`shift`/`indexOf` and every unmatched end tag scans it. The tree builder keeps htmlparser2's rules (implied end tags, void elements, foreign content, the ignored second `<form>`) on a push/pop stack with a count per open name, so an unmatched end tag is O(1). The walker applies the same implied end tags to what it writes, which makes the output a fixpoint (`sanitize(sanitize(x)) === sanitize(x)`, checked for every corpus message). `domhandler` stays in `package.json` only as htmlparser2's own dependency.
- **Rules.** Elements: an allowlist (text formatting, tables, lists, `img`, `a`, `details`), everything else unwrapped (text kept) or dropped with its content (`script`, `meta`, `link`, `base`, form fields, `iframe`, `frame`, `object`, `embed`, `svg`, `math`, `template`, `noscript`, media). `<noframes>` fallback text is re-parsed once and sanitized, since the frames it stands for are dropped. Attributes: an allowlist; `href` keeps http, https, mailto and tel (WHATWG-parsed, written back normalised) with `target="_blank" rel="noopener noreferrer"`, and fragments; `src`, `background` and CSS URLs become `cid/<n>`, `img/<n>` (images on) or nothing, plus raster `data:` in `<img src>` only (the CSP allows `img-src data:`). Ids, anchor names, `headers`, ARIA id references and `#id` selectors move into an `m-` namespace (DOM clobbering: a hyphenated name is no JavaScript identifier). CSS: at-rules other than `@media`, `@supports`, `@keyframes`, `@layer` and `@container` go with their blocks; strings inside `image-set()` and `image()` are URLs; address-like strings elsewhere are emptied; `attr()` and `expression()` go, and so do `var()` and `env()` inside image functions; comments become `/**/`; `</` never appears outside a CSS string. Trackers: remote images that are hidden (attribute, inline style or a hidden ancestor), 1 px or less in a dimension, at most 2x2, or unsized with a beacon-like path, removed and counted. Quotes: Gmail, Yahoo, Proton, Apple (`blockquote type=cite`), Thunderbird and Outlook markers and "Original/Forwarded message" lines, found with a bounded look-ahead (the earlier branch's look-ahead was quadratic on deep mail). The document declares `<meta charset="utf-8">` within its first 1,024 bytes, and ESC and NUL become U+FFFD everywhere.
- **Limits.** 512 KiB of markup (style text not counted), 20,000 elements, 256 KiB of `<style>` text per message (a block over the budget is dropped; one that alone is over it is cut before tokenizing, so a 5 MB stylesheet costs 0.8 ms and the text after it survives), and `style` attributes over 32 KiB are dropped. A clipped message ends with "This message is very long, so Aplos shows only its beginning." Gmail clips at about 100 KB; 20,000 elements is about four times a large newsletter.

## 2026-10-31 eng-html html-3: fixes from the Opus security review (VERDICT FIX)

- **MEDIUM, fixed: nested `<noframes>` re-parsing was quadratic.** The fallback text was re-parsed with fresh limits after one regex pass removed nested `<noframes>` tags, and `<nofr<noframes>ames>` turns back into `<noframes>` when its inner tag is removed, so every level re-read everything below it. ## 2026-10-31 eng-html html-3: class whitespace kept as written in markup too (correction to #177)

- **Correction.** The last bullet of the #177 section ("Whitespace in a rewritten value is kept as written (the choice)") gave the wrong reason and described only half of the code.
