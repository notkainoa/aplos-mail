## 2026-10-15 — Multi-provider, serverless architecture

- Researched two open-source mail backends (Redakt, Superlocal) for patterns only; no code copied. Adopted: incremental provider sync from a stored cursor, a per-account rate gate, durable local operations with undo, a send hold that cannot double-send, content-hash AI caching, paged queries with change events. Rejected for Aplos: a hosted Postgres/web backend, multi-user tenancy and running our own mail server (Redakt's Stalwart approach): the user's mail host is the sync server.
- Target shape: one platform-free TypeScript engine (`src/engine`) shared by desktop now and a React Native app later; platform specifics enter through small ports (SQL database, secure storage, sockets, OAuth, background scheduling). Providers implement one contract: `sync(cursor)` returning changed threads, flag-only updates, removals and the next cursor; `apply`; `send`; `fetchBody/attachment`; capabilities. Planned adapters: Gmail API, Microsoft Graph (MSAL public client, delta per folder), JMAP (Fastmail), IMAP+SMTP (iCloud, Yahoo, AOL, generic; own threading from Message-ID/References). Proton only through Bridge on desktop. TypeScript over a Rust core because all current and planned runtimes run TypeScript; raw IMAP sockets on mobile stay behind a port.
- Storage is SQLite through Node's built-in `node:sqlite` (Node 24 and Electron 44 both ship SQLite 3.5x with FTS5), so no native module rebuild is needed for Electron. The engine owns a minimal synchronous SQL port so mobile can use op-sqlite/expo-sqlite later. The existing `state.json` is imported once and kept as `state.json.imported`.
- Aplos-only workflow state (Done vs. merely read, Later, todos, due dates, reminders) is kept locally and survives syncs; the host's labels/folders are authoritative for read, star, trash, spam and inbox membership. A thread returns to Home when a new message arrives, when Gmail moves it back to the inbox while the matching Done/Later action is "archive", or when it lands in Trash/Spam. Cross-device sync of the workflow log goes later through an encrypted hidden mailbox folder (no Aplos server).
- Gmail: the first sync fetches the newest 500 threads instead of the whole mailbox; afterwards `history.list` from the stored `historyId` drives sync. Threads that only changed labels are refreshed with `format=minimal`; added messages trigger a full thread fetch; a missing thread is removed locally; an expired cursor (404) falls back to a fresh bounded sync. Older mail is reached through Gmail search, which is limited to 100 threads per query.
- Background sync runs every 60 s and when a window gains focus, behind a per-account gate (single flight, at least 15 s between automatic syncs, exponential backoff after failures up to 15 min). "Sync now" bypasses the interval but not the single-flight rule.
- Triage is local-first. Each change is applied at once and written, in the same transaction, to an `ops` table as a provider change (remote ID, the status it started from, the patch). A worker sends ops in order per account; one failure holds back only that account's later ops, so a thread never gets an older change after a newer one. Failures retry after 30 s doubling to 15 min; "Sync now" retries at once. A 404 drops the op, since the thread is gone. Sync sends ops before pulling, and threads with an op still queued keep their local status, read, star and labels (new arrivals and removals still apply). Undo and reminders go through the same queue. Disconnecting an account drops its ops.
- Sending can never double-send. Each draft gets one Message-ID on the sender's domain when it is first sent, kept across retries. Before calling Gmail, the draft is marked with `sendAttemptAt`. A network error or 5xx is uncertain: Aplos looks for the Message-ID in Sent mail (`rfc822msgid:`) and treats a match as sent; otherwise the draft keeps an error asking the user to check Sent mail. A definite rejection (4xx) is reported as is. After a crash, drafts with `sendAttemptAt` are settled only from Sent mail and never sent again automatically.
- Live push needs a server for Gmail and Graph, so desktop polls. A later optional push relay may store only push token ↔ mailbox ID, never tokens or content. Google restricted scopes need verification; the CASA assessment applies when data passes through a third-party server, so any relay or AI proxy must be checked with Google first. Groq on mobile needs a user-entered key or a proxy; desktop keeps reading `GROQ_API_KEY` from the backend environment.

## 2026-10-16 — Outlook, IMAP (iCloud), JMAP (Fastmail), CalDAV and discovery

- One `MailProvider` contract (`src/engine/provider.ts`) with capabilities per account (`labels`, `importance`, `aliases`, `signatures`, `calendar`, `serverSearch`). Thread IDs are `${account.id}:${remoteId}`. Folder hosts report role labels (INBOX, ARCHIVE, SENT, TRASH, SPAM) so the service can describe intent the same way for every host: a patch whose `labels` lack INBOX means "archive", labels with INBOX mean "keep in the inbox". The read/unread Done and Later actions always pass explicit labels, so no host infers an archive from the status alone.
- Each adapter keeps its own index (message → thread, folder, UID/flags) in a `provider_memory` table (schema v3) that disconnect clears. Secrets (app passwords, API tokens, OAuth tokens) live in per-provider vault files, each entry encrypted with Electron safeStorage; they never enter app state, logs or the renderer.
- Microsoft Graph: public client with PKCE on a `http://localhost` loopback redirect (Entra ignores the port only for `localhost`); `Prefer: IdType="ImmutableId"` so moves keep IDs; conversations are threads; first sync is the newest 500 messages across the five role folders, then per-folder delta; sends go as MIME through `/me/sendMail` because Graph's JSON path cannot set `internetMessageId`, which the double-send guard depends on. Sends above about 3 MB are refused rather than sent through an upload session that would lose the Message-ID. Graph cannot save meetings without notifying guests; the README says so.
- IMAP/SMTP: imapflow and nodemailer behind small `ImapSession`/`SmtpSender` interfaces (also the mobile seam). Threads come from Message-ID/In-Reply-To/References, with keys derived from the first Message-ID so they survive memory loss; per-folder cursors use UIDVALIDITY/UIDNEXT and CONDSTORE when offered. iCloud does not file SMTP mail in Sent, so Aplos appends a copy; other hosts are checked first and appended only when missing. Calendar for IMAP accounts is CalDAV through a separate `CalendarBackend` with an original iCalendar parser (no library); it never writes an ORGANIZER, so servers do not send invitations, and it refuses to edit one occurrence of a repeating event.
- JMAP: Fastmail with an API token; Email/changes plus Thread/changes; sends create the draft and the EmailSubmission in one request that moves it to Sent on success, and first destroys any leftover draft with the same Message-ID. Fastmail calendar is not connected: API tokens do not grant CalDAV.
- Discovery is platform-free (`src/engine/discover.ts`): known consumer domains, then MX over DNS-over-HTTPS (Cloudflare, then dns.google), then HTTPS-only autoconfig (the domain, then Thunderbird's ISPDB), then common host names marked as a guess. Configs that point at loopback or private addresses are ignored; Proton addresses are told Bridge is not supported yet, because Bridge's self-signed certificate does not pass strict TLS. The domain checker reads MX, SPF (with the 10-lookup limit), DKIM (known selectors per host), DMARC and MTA-STS records and explains each fix.
- Review fixes adopted for the shared contract (GPT-6.1-Sol): a send whose outcome is unknown keeps its marker and Message-ID across errors and edits, and every retry looks in Sent first; real accounts whose adapter is missing keep their queued changes and never complete a send locally; threads changed while a sync is in flight are protected from that sync's answer even after their change has flushed; a late host answer cannot re-queue a change that disconnect discarded; a local sent copy without a host thread is replaced when the host's copy with the same Message-ID syncs; `'primary'` resolves to the real default calendar before saving and duplicate checks; server URLs with embedded passwords are refused.
- Not adopted from that review: replacing `Partial<Thread>` patches with explicit host operations. Each adapter maps the patch plus the labels convention above, and the tests pin that mapping; revisit if a host needs operations the patch cannot express.

## 2026-10-16 — M26 engine process, change events, paged reads

- The service runs in an Electron utility process (`src/main/engine-host.ts`, built to `dist/main/engine.cjs`). The main process keeps windows, menus, notifications, links (`openExternal` is a call back into main) and the keychain. Messages use a small typed protocol over the utility port (`src/main/engine-rpc.ts`: init, invoke/result/error, event, call/reply, close/closed); the same code runs over a `worker_threads` channel in tests. The browser preview keeps the service in-process.
- The utility process cannot reach safeStorage, so credentials are sealed with a random 256-bit data key (AES-256-GCM, `APK1` prefix) and the keychain protects only that key (`engine-key.bin`). Main unwraps it at start and passes it to the engine in memory. A key file that cannot be read (locked keychain) is never replaced, since that would orphan every saved credential; accounts then report that the keychain must be unlocked. Credentials sealed directly with safeStorage by earlier builds are re-sealed once at start; entries the keychain cannot open are left as they were.
- If the engine process stops unexpectedly, waiting requests fail with a message, main starts a new engine and sends every window a fresh snapshot. More than three stops in a minute ends the restarts with an error, so a crash loop stays visible.
- Each commit reports what the database save actually wrote (`StoreDiff`: changed and removed thread IDs, changed collections and fields), and windows receive only that as a `changes` event. Small collections (accounts, drafts, events, conversations) are sent whole when they change; threads as rows. Every change carries the engine run (`epoch`) and a commit number (`rev`). A window applies changes in order, holds those that arrive before its snapshot, ignores old ones, and fetches a new snapshot when one is missing or the epoch changed (`src/shared/live.ts`).
- The main window starts from the newest 400 threads (`state.get {threadLimit}`) and reads the rest in pages of 2,000 with a keyset cursor (`threads.page {before:{date,id}}`), so new or removed mail during paging cannot shift pages. A page never restores a thread a later change removed and never overwrites a newer copy. Pop-out windows still load everything at once.
- Not done: windows still hold every thread once paging finishes, with message bodies. Loading bodies on demand is the next step if very large mailboxes need it.

## 2026-10-16 — M29 workflow sync between devices

- What syncs: each thread's workflow fields (Done/Later/New, reply status, due date, todo, reminder and whether it fired, hidden from Home). Trash and Spam are host state and are not part of it. The log is last-writer-wins per thread (`src/engine/workflow.ts`, platform-free); a merge is commutative, associative and idempotent. Entries are keyed by the host's thread ID (Gmail, Graph, JMAP), or by the thread's root Message-ID for IMAP, whose thread IDs are built per device.
- Only real user edits enter the log (triage, undo, Home hide, fired reminders). Each edit is recorded at edit time as a snapshot of the thread's workflow fields with its edit time and a generation number, in the same transaction as the edit; that edit time, not the sync time, decides conflicts. Mail sync changes (a host archive becoming Done) do not count, or they would override another device's Later. The first device to turn sync on seeds the log from its existing Later, todos, due dates and reminders (timestamped with the thread's last message, so real edits win); a device that joins takes the shared log as it is. Each device remembers which winning entry it applied per thread, so an entry applies once, and an entry for a thread downloaded later (through search, say) still applies when it arrives. A newer message from someone else keeps the thread on Home even if another device marked it Done.
- A round reads every stored copy, merges all of them with this device's edits, writes one new copy and then removes only the copies it read. Two devices writing at once therefore never delete each other's copy; the next round folds both. An edit made while a round is in flight is not acknowledged and its thread is not patched by that round. What a round remembers is saved together with the patches it applies, so a crash in between redoes the round.
- Compaction drops plain entries older than 180 days and records a floor; a merged entry older than another log's floor is rejected, so a long-offline device cannot bring back a Later that was cleared and compacted away.
- Storage: small marked messages in a hidden "Aplos Mail Data" folder per account (a name the user is unlikely to have; a user folder named "Aplos" is ordinary mail). Only messages carrying Aplos's own marker count as records (a header for Gmail and IMAP, a named extended property for Graph, a keyword for JMAP), so user mail is never read or deleted even if it sits in that folder. Gmail uses a label with list and message visibility hidden, `messages.insert`, and trashes replaced copies, because `gmail.modify` cannot delete. Graph uses a hidden folder; IMAP an unsubscribed folder; JMAP an unsubscribed mailbox without a role. Normal sync and search never surface it.
- Encryption: a 28-symbol sync code (130 random bits plus a 2-symbol check, Crockford base32, entered in any case and spacing) → scrypt (N=2^15, random salt per write) → AES-256-GCM with the header authenticated; a separate check value tells a wrong code from damaged data. The code is kept in the credential vault (`workflow-sync.enc.json`), never in app state. Data sealed with a different code or a newer format is reported and never overwritten; damaged data is replaced; a copy too large to open is kept, never replaced, and writes trim old entries until the log fits.
- When: after each account's mail sync, at most every 5 minutes for automatic syncs unless there are edits to share, and on every manual sync. Writes happen only when the merged log differs from the host's copy. Patches from other devices change local state only; the other device already told the host about its own archive or move.
- Not done: no live mailbox verification; device clocks decide conflicts; the browser preview cannot sync devices, since it has no credential vault.

## 2026-10-16 — Second review round (GPT-6.1-Sol) for adapters, engine host and device sync

- Provider indexes are saved with the mail they describe. Writes an adapter makes to provider memory while `sync` (or a workflow round) runs are held in a stage (`src/main/memory-stage.ts`, AsyncLocalStorage) and written in the same SQLite transaction as the threads and the new cursor. A failed or interrupted sync leaves index and cursor as they were and replays. Keys carry versions: if another operation (a move during sync) rewrote a key the sync read or wrote, the sync's result is dropped and fetched again, up to three times. Adapters hold no index copies in process memory between calls.
- A send whose earlier attempt is unresolved is never resubmitted by a normal retry, for every host: not finding it in Sent proves nothing (Graph and JMAP deliver asynchronously; SMTP has no idempotency). Compose offers "Send anyway" after a warning that recipients may get two copies; the choice covers one attempt. JMAP additionally recognizes a submitted message by its submission record even when the move to Sent failed, and never destroys a draft that has a submission.
- A sync that answers after its account was disconnected or reconnected is discarded (account generation), so disconnect cannot be undone by a late answer.
- Hosts that tell Aplos where to go are held to HTTPS on every hop: JMAP session endpoints and redirects, CalDAV principal/home/event addresses and redirects, autoconfig redirects. Autoconfig results naming loopback, private, link-local or CGNAT addresses, in any spelling or after DNS resolution (system resolver on desktop, DNS-over-HTTPS in the platform-free engine), are ignored. Servers the user types by hand are not checked: self-hosted servers on a home network are legitimate.
- Calendar: repeating events and meetings with invited guests are read-only in Aplos (CalDAV), because changing them would rewrite the series or let the server email guests; guests Aplos adds are written with `SCHEDULE-AGENT=CLIENT` and no organizer. Each event keeps the ETag it was read at and saves fail rather than overwrite a newer version, also across restarts. Edited times stay in the event's own time zone; custom VTIMEZONE gaps resolve like IANA zones. Occurrences of one series have their own IDs and are all kept.
- IMAP: cached UIDs are used only while the folder's UIDVALIDITY matches; otherwise messages are found again by exact Message-ID. Without MOVE or UIDPLUS a move copies and marks the source deleted without EXPUNGE, so unrelated deleted messages are never purged. Refused STOREs and moves are errors; explicit flag changes are always sent. Thread keys come from the References root, so they survive index loss.
- Graph and JMAP: a partly deleted conversation is refetched in full; attachment lists and initial queries follow paging and the server's object limits; JMAP full fetches request body values and capture states before the first query, then replay changes so mail arriving during the first sync is not skipped.
- Domain check: SPF stops counting at `all` and ignores `redirect` when `all` exists; DMARC with duplicate tags or invalid `p`, `sp` or `pct` fails instead of passing.
- Engine host: a failed snapshot fetch is retried with backoff (0.5 s doubling to 30 s) so a window never freezes on a gap; replacement engines that fail before ready count toward the restart limit and are terminated; credential migration runs per file without withholding the data key; the data folder is created before the key is loaded.
- Accepted risks: a name that does not resolve is allowed by the autoconfig host check (otherwise offline guesses vanish), and DNS rebinding at connect time is not prevented; two devices turning sync on before either writes both seed (seeds are timestamped with message dates, so real edits still win); app data written by earlier development builds (no marker) is ignored.
