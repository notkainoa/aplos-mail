## S1. [blocker] [scopes] Plan/confirm and Ask/decide are tagged triage but can send calendar invitations to any address

- **Where:** packages/contract/src/api/compose.ts:68-72 (Plan/confirm, scope 'triage', fields: partial(EventFields)); packages/contract/src/schemas/calendar.ts:97 (EventFields.attendees, up to 500 addresses); packages/contract/src/api/ai.ts:106-111 (Ask/decide, 'triage', accepts an addEvent Proposal whose event is EventFields, schemas/ai.ts:109); generated listenerMethods lines 384, 340
- **Problem:** The contract README says `send` covers 'Anything that sends mail or notifies other people: submissions, RSVPs, event edits with guests' and `triage` covers only 'Reversible mailbox and calendar changes' (README.md:52-54). Event/set is tagged `send` for exactly this reason (compose.ts:50-54). Plan/confirm takes `fields.attendees` and writes the event to the provider calendar, and it has no `notify` flag. So a triage-only tool can create a provider event with up to 500 guests, which makes Google email invitations. Ask/decide does the same with an LLM-written addEvent proposal, and that proposal can be steered by prompt injection from hostile mail (ARCH 8.5). Neither method carries `audit`, so ARCH 12.3.5 ('an audit_log row for every send') is not met either.
- **Suggested fix:** Remove `attendees` from Plan/confirm's `fields` (use Omit/partial without attendees), or tag Plan/confirm `send` with audit. For Ask/decide, either tag it `send` plus audit, or state in the contract that accepting an addEvent proposal that has attendees needs the caller to hold `send`, and that the engine checks this per proposal kind. Add a registry test: any input reachable at triage scope may not contain an `attendees` or recipient field.

## S2. [blocker] [scopes] A listener client can grant background-AI consent and redirect AI traffic (keys and mail text) without the owner

- **Where:** packages/contract/src/api/ai.ts:153-158 (Consent/grant, admin, not uiOnly); packages/contract/src/api/core.ts:26-31 (Settings/set, admin, not uiOnly); packages/contract/src/schemas/settings.ts:119 (ai.providers: record(any id) -> {address, paid}); packages/contract/src/api/account.ts:56-61 (Account/set aiAllowed); generated listenerMethods lines 351, 402, 325
- **Problem:** ARCH 8.3 says 'A versioned consent card appears before the first background pass, naming the provider, model and what is sent', and 'the unpaid Gemini tier ... is mail-eligible only with a paid key'. ARCH 12.2 says AI keys are 'never printed, logged'. The secret methods (Ai/setKey, Ai/removeKey, Ai/pasteKey) are kept off the listener. But an admin tool on the socket or HTTP can still do all of this: Consent/grant (agree to the card for the owner), Account/set {aiAllowed:true} on every account, Settings/set {ai:{providers:{custom:{address:'http://attacker'}}}} or `gemini.paid:true`, and features.* pointing at that provider. Result: all mail goes to a server the tool picked, with CUSTOM_AI_API_KEY attached as the bearer. The `providers` record also takes any provider id, so an `address` for openai or anthropic is schema-valid, which could redirect a hosted key if the engine honours it. The define.ts comment reserves uiOnly for 'listener and client management, content export', and consent is the owner's informed agreement, so it belongs there too.
- **Suggested fix:** Mark Consent/grant `uiOnly`. Split the safety-relevant settings out of the listener's Settings/set: `ai.providers.*.address|paid`, `ai.features`, `mail.remoteImages`, `mail.imageAllowList`, `mail.undoSendSeconds`. Either refuse patches touching these from `caller.kind==='listener'` (state it in the summary), or move them to a uiOnly `Settings/setSensitive`. Restrict the `providers` record keys to ollama, lmstudio, custom and gemini with a closed enum.

## S3. [blocker] [scopes] Plan/confirm and Ask/decide can create provider calendar events with guests (invitations go out) using only triage scope, with no audit row

- **Where:** packages/contract/src/api/compose.ts:68-71 (Plan/confirm: scope 'triage', no audit, fields: z.partial(EventFields)); packages/contract/src/schemas/calendar.ts:97 (EventFields.attendees, up to 500); packages/contract/src/api/ai.ts:106-110 (Ask/decide: scope 'triage', no audit) accepting packages/contract/src/schemas/ai.ts:109 (Proposal 'addEvent' with event: EventFields); compare compose.ts:50-54 (Event/set is scope 'send' + audit because it 'may notify guests')
- **Problem:** ARCH 12.3 item 5 requires 'an audit_log row for every send ... by a non-UI client' and item 6 says 'send and destructive actions need an explicit grant and a confirmation in the app'. Event/set is tagged send+audit because writing an event with attendees sends invitations. Plan/confirm takes the same EventFields (attendees included) and writes to the provider calendar under 'triage'. Ask/decide accepts an 'addEvent' proposal under 'triage', and that proposal's attendees come from model output over untrusted mail (ARCH 8.5). Both are in listenerMethods, and neither is audited. Scenario: a CLI tool granted only triage calls Plan/confirm {fields:{attendees:[...500 addresses]}}. Or a prompt-injected email gets Ask to propose an event with outside attendees, and a triage-scoped agent accepts it. Either way invitations go out from the owner's account with no send grant and no audit row. Plan/confirm has no `notify` argument either, so whether guests get emailed is not defined.
- **Suggested fix:** Give Plan/confirm scope 'send' + audit, or drop `attendees` from its `fields` (Pick<EventFields> without attendees) and fix notify=false. For Ask/decide, mark it send+audit, or split it: Ask/decide stays triage for 'triage' and 'reply' proposals, and a new Ask/acceptEvent (send, audit) handles addEvent. Add a registry test asserting that every method whose input can carry attendees or recipients is scope send and audited.

## S4. [should-fix] [scopes] Operation/undo, Operation/retry and Queue/retry re-run other scopes' operations (triage or admin can send)

- **Where:** packages/contract/src/api/mail.ts:74-86 (Operation/undo, Operation/retry: triage, any opId); packages/contract/src/api/admin.ts:14 (Queue/retry: admin, any queue item including kind 'submission', schemas/session.ts:136); packages/contract/src/api/compose.ts:51 ('held briefly for undo')
- **Problem:** Event/set, Event/rsvp, Unsubscribe/run and Submission/set return receipts whose opIds go into the same Operation table. Operation/undo 'queue[s] its inverse' after the hold, and the inverse of a created event with guests is a delete that sends cancellations. The inverse of an RSVP is another RSVP, and the inverse of a Submission/set {type:'undo'} is a send. Operation/retry re-executes a failed Event/set. Queue/retry on a 'submission' item re-sends mail, and it is reachable with `admin` alone, even though scopes are not hierarchical and ARCH 12.3.6 says 'send ... need an explicit grant'. Nothing in the contract ties these generic commands to the scope of the operation they act on, so E7's acceptance case 'a read client ... cannot call Submission/set; draft can save but not send' passes while the same effect is reachable another way.
- **Suggested fix:** State the rule in the contract (README and the summaries): Operation/undo, Operation/retry, Queue/retry and Queue/discard require the caller to hold the scope of the method that created the target operation or item. Have Operation and QueueItem carry `scope` (additive, open enum) so the engine and the UI can check it. Add a conformance case: a triage client's Operation/undo on an Event/set opId gets `forbidden`.

## S5. [should-fix] [transports] Blob, window, run and connect handles are not bound to the caller, so uiOnly Data/export is readable with read

- **Where:** packages/contract/src/api/admin.ts:96-100 (Data/export uiOnly, returns blobId); packages/contract/src/api/mail.ts:142-147 (Blob/get read, any blobId; also Blob/release read, in mcpMethods line 439); mail.ts:16-30 (View/move|unwatch|hold by windowId); ai.ts:104 (Ask/cancel by runId); account.ts:52 (Account/cancelConnect by connectId); mail.ts:113-116 (Mail/release|toggleQuotes by url)
- **Problem:** define.ts:35 says uiOnly methods are 'never the socket, HTTP or MCP (... content export)'. Data/export ('accounts, settings, workflow, drafts, conversations') is uiOnly, but its output is a bare blobId that any `read` client, including the MCP adapter, can fetch with Blob/get or `GET /v1/blob/:id`. The same applies to Diagnostics/export (admin), a dictation the renderer uploaded, and Message/original blobs. Id is free text (common.ts:45), with no rule that ids are unguessable or owned by a connection. Handles for windows, runs, connects and frame URLs, plus opId idempotency keys, are also global, so one client can release, cancel or replay into another client's handles. ARCH 12.3.4 asks for 'typed, scoped operations only'.
- **Suggested fix:** Add one contract rule (README 'Scopes and transports' and the summaries): blob, window, run, connect and frame handles are scoped to the connection, or to the clientId for listener clients, that created them. Another caller gets `notFound`. Idempotency is keyed by (clientId, opId). Blob ids are at least 128 random bits. Blobs made by uiOnly methods are readable only by Electron windows. Add a conformance case: a listener Blob/get on a Data/export blob returns notFound.

## S6. [should-fix] [scopes] draft scope (and MCP) can rewrite a scheduled or held send, and Draft/destroy is exposed to MCP with no confirmation

- **Where:** packages/contract/src/api/compose.ts:10-19 (Draft/set and Draft/resolve, scope 'draft', no refusal while Draft.submissionId is set); packages/contract/src/schemas/compose.ts:55-56, 69-88 (Submission records no revision or content snapshot), 93 (send pins `revision` only on input); generated mcpMethods lines 444-447
- **Problem:** ARCH 7.1 says Gmail sends use `drafts.send` when a synced remote draft exists, which sends the provider draft's current content. Draft/destroy is 'refused while it is sending', but the contract says nothing similar for Draft/set or Draft/resolve while a submission is queued or scheduled. So an MCP agent (draft scope, which ARCH 12.3.6 exposes without a grant) can change `to`, `bcc` or `html` of mail the owner already approved for send-later, and the changed message goes out. That turns draft into send. Draft/destroy, which also deletes the provider draft, is in mcpMethods, while ARCH 12.3.6 says 'destructive actions need an explicit grant and a confirmation in the app'.
- **Suggested fix:** In Draft/set and Draft/resolve, state that the call is refused (`stateMismatch`, 'This message is waiting to send. Undo the send to edit it.') while `submissionId` is set. Also state that a submission sends the revision it was given, and add `revision` to Submission. Remove Draft/destroy from mcpMethods, or give the registry a `confirm` tag (next finding) and set it on Draft/destroy.

## S7. [should-fix] [scopes] No registry tag or frame for the in-app confirmation that ARCH 12.3.6 and E7 require

- **Where:** packages/contract/src/registry/define.ts:25-39 (MethodSpec has secret, uiOnly and audit, but no confirm); packages/contract/src/wire.ts:56-69, 95-136 (no confirmation-request HostEvent or frame); listener-reachable destructive methods: account.ts:68 Account/disconnect, ai.ts:145 Demo/remove, ai.ts:114 Conversation/destroy (tagged 'ai'), thread.act with a whole-view selector (mail.ts:55-60)
- **Problem:** ARCH 12.3.6: '`send` and destructive actions need an explicit grant and a confirmation in the app'. Plan 10 E7.6: 'the engine emits the request; the dialog is plan 30's', and E7 acceptance: '`send` needs a grant and raises a confirmation request'. F1 is supposed to freeze 'all frames', but the contract has no confirmation-request event, no way to report it as pending, approved or denied, and no per-method marker saying which methods need it. As it stands, an admin tool can call Account/disconnect ('Remove an account and everything Aplos stored for it') with no owner in the loop. Conversation/destroy, a delete, is tagged `ai`, which means 'spends the AI budget'.
- **Suggested fix:** Add `confirm?: true` to MethodSpec and generate `confirmMethods`. Set it on every send-scope method, Account/disconnect, Demo/remove, Draft/destroy, Conversation/destroy and Queue/discard. Add a HostEvent `confirm {requestId, clientId, method, label}` and a uiOnly `Confirm/answer {requestId, allow}`, plus an error type or reasonCode for 'waiting for confirmation' or 'declined'. Retag Conversation/destroy to `triage`.

## S8. [should-fix] [transports] The engine's dispatch is default-allow and never checks the Caller it is given

- **Where:** packages/engine/src/methods/index.ts:72-79 (dispatch runs any served method; the doc says the transport 'has checked' the scope); packages/engine/src/methods/types.ts:11-16 (Caller.kind and scopes exist but are not used)
- **Problem:** ARCH 9.4 puts the window check only in preload, and the listener check in each transport. dispatch serves `host` methods (Mail/serve, Notification/claim and ack), uiOnly methods (Clients/grant, Listener/set, Data/export) and secret methods (Ai/setKey, Workflow/code) to any connection. Four transports (MessagePort, main's control connection, socket, HTTP/MCP) are built by different work packages (WP3.4, WP7.1, WP7.4). One missing check in any of them means a read token reaches Submission/set, or a window port reaches Notification/claim. The tables needed for a central check (methodScope, hostMethods, listenerMethods) are plain strings with no zod, so the check costs nothing against the 400 KB budget.
- **Suggested fix:** In dispatch, before calling the handler: refuse `host`-scope methods unless caller.kind==='host'. Refuse non-listenable methods (uiOnly, secret, desktop) when caller.kind==='listener'. Refuse when methodScope[method] is not in caller.scopes. Then write the audit_log row for auditMethods when kind==='listener'. Log `listener.request_denied {why:'scope'}`. Add a unit test that calls dispatch with a listener Caller holding ['read'] and expects `forbidden` for Submission/set and Mail/serve.

## S12. [should-fix] [transports] Hello frame has no token field, so the socket binding's 'token in the hello frame' cannot be expressed (and a strict parse would strip it)

- **Where:** packages/contract/src/wire.ts:27-28 (Hello = {v, apiVersion, appVersion?, client:{name, kind}})
- **Problem:** ARCH 9.4 says the CLI/MCP binding is a 'Unix socket run/engine.sock ... NDJSON frames, token in the hello frame'. ARCH 12.3 item 2 requires 'A per-client token on every request'. The frozen Hello schema has no token. It is a z.object, so parsing a hello through it silently strips any extra `token` key. The contract also defines no hello reply (granted scopes, `unsupported` with the upgrade message from ARCH 9.5). Socket lanes would each invent their own auth handshake outside the contract after C1.
- **Suggested fix:** Add `token: line(100)` to Hello. Document it as transport-only: never logged, never echoed, and stripped before any handler sees it. Add a HelloReply {apiVersion, scopes, clientId} | ErrorBody. Also state in wire.ts that HTTP carries the token in `Authorization: Bearer`, matching the openapi securitySchemes.

## S13. [should-fix] [scopes] Blobs are not bound to a client: Blob/get (read, MCP) can read uiOnly/admin export blobs, Blob/release (read) can delete others' blobs, and Blob/put has no size cap in its schema

- **Where:** packages/contract/src/api/mail.ts:136-147 (Blob/put scope draft, Blob/get scope read, Blob/release kind command scope read); packages/contract/src/schemas/common.ts:84 (Bytes = z.instanceof(Uint8Array), no length check) and :45 (Id = any 1-1000 char string); packages/contract/src/api/admin.ts:23-26 (Diagnostics/export -> blob) and :97-99 (Data/export uiOnly admin -> blob)
- **Problem:** ARCH 12.3 item 5 defines scopes, and the registry marks Data/export uiOnly so tools can never pull an export of accounts, workflow, drafts and conversations. But its result is a blobId, and Blob/get is read-scoped, listener- and MCP-exposed, and takes any Id. Nothing in the contract says blob ids are unguessable or owned by the connection that made them. So a read-scoped MCP tool that learns or predicts the id (a ULID is time-ordered) gets the uiOnly export. Blob/release is a deleting command under 'read', so a read-only tool can drop a blob backing a draft attachment it saw via Draft/get. Blob/put's summary promises '25 MB at most', but the input validator ARCH 9.3 places 'at every host boundary' enforces no size, so the cap depends on each transport remembering it.
- **Suggested fix:** In the contract, state that blob ids are 128-bit random capabilities owned by the creating client/connection, and that Blob/get and Blob/release refuse other owners with notFound. Make Blob/release scope match Blob/put ('draft'). Add `.check(z.refine(b => b.byteLength <= 25*1024*1024, ...))` to Blob/put.bytes, or a `tooLarge` refine, so every host enforces it. Alternatively, have uiOnly methods return bytes only to Electron windows rather than a listener-readable blob.

## S14. [should-fix] [logger] Diagnostics bundle and wire errors carry ClassifiedError unredacted: the Logger redacts only its own copy, so the 'already redacted by the Logger' guarantee is false

- **Where:** packages/contract/src/schemas/session.ts:150-153 and :169-170 (DiagnosticsBundle 'content-free by construction'; errors[].error: ClassifiedErrorSchema, 'providerMessage is already redacted by the Logger'); packages/contract/src/errors.ts:39-41 (item: z.string(), providerMessage: z.string().max(300)) and :77-78 (ErrorBody.classified); packages/engine/src/diag/log.ts:58-96 (cleanError builds a new object for the sink and leaves the caller's record untouched); session.ts:144 (QueueItem.problem.message: z.string())
- **Problem:** ARCH 11 requires a bundle that is 'content-free and previewed before saving' and, as its acceptance test, one that 'contains no bodies, subjects or tokens'. The Logger hashes `item` and runs `providerMessage` through redactText only on the record it writes. The governor's ClassifiedError (from F3 and governor_state) keeps the raw provider text and the raw remote item id. The bundle schema accepts both as free strings, so a builder that reads governor_state or the queue (the obvious source of 'recent errors') ships raw provider text, unhashed provider item ids and an unbounded QueueItem.problem.message. The same raw record also travels in ErrorBody.classified, Operation.error and WindowBody.error to listener clients. The schema cannot enforce the comment's claim.
- **Suggested fix:** Make redaction happen where the record is made: the governor or ProviderError constructor calls redactText and hashAddress (or one shared `classify()` does). Alternatively, build the bundle's errors only from ring-buffer records that went through the Logger. Use a branded `RedactedText` and `HashedId` in ClassifiedErrorSchema. Cap QueueItem.problem.message and Session.engine.parked.message. Extend the E0 canary test to Diagnostics/preview: CANARY strings in providerMessage, item and the queue problem must not appear.

## S16. [should-fix] [mail-frame] Mail/frame, Mail/release and Mail/toggleQuotes are open to read-scoped listener and MCP clients, which can churn the 64-token pool and evict the reader's live frames

- **Where:** packages/contract/src/api/mail.ts:102-117 (scope 'read', not uiOnly); packages/contract/scripts/generate.ts:24 and :36 (so they land in listenerMethods and mcpMethods)
- **Problem:** ARCH 10 says the token is a '128-bit single-render token' served only by main's protocol handler. Plan 10 E4 item 3 says 'at most 64 live; dropped when the reader replaces them'. A frame URL is useless outside an Electron window, since Mail/serve is correctly host-only and the HTTP binding has no aplos-mail route. But listener clients can still mint tokens. A read-scoped tool calling Mail/frame in a loop pushes the owner's open reader frames out of the 64-slot pool, so they go blank, and the contract does not tie a token to the connection that minted it. This is the 'single-purpose' property ARCH 10 asks for. Releasing or toggling by URL is also not tied to the minting connection.
- **Suggested fix:** Mark Mail/frame, Mail/release and Mail/toggleQuotes `uiOnly: true` (MCP and CLI use MessageBody/get for text). Also document that the engine binds each token to the minting connection, so Mail/release and Mail/toggleQuotes refuse other connections. Regenerate the allowlists and openapi.json.

## S21. [question] [logger] How do main-process events (update.*, crash.recorded for main/renderer/gpu) reach the log: a second sink on the same file, or through the engine?

- **Where:** packages/contract/src/log/events.ts:177 and :186-188 (emitters 'eng-host' and 'plat-release', process: main|renderer|gpu); apps/desktop/src/host/logsink.ts:33-70 (per-instance `size` counter, rename-based rotation); packages/engine/src/store/index.ts:43 (install_salt lives in mail.db)

- **Suggested fix:** Specify a single writer.
