# Blob area and html-4 slice 3: `Blob/put|get|release`, `Attachment/get`, `Message/original`

Status: design note, 2026-11-04, before any code (HANDOFF next action 1). Owner of the note: Engine (eng-contract), with eng-html, eng-store, eng-time, eng-host and prov-gov/prov-gmail for their halves. Nothing here is built.

## In plain English

A "blob" is a file the app holds for a moment or for a draft: a file you attach, a voice clip, an attachment you open, the raw "Show original" text. The engine cannot touch the disk, so the Mac side (the host) keeps every blob as one private file in `<dataDir>/blobs/`, and the engine keeps the list of which blobs exist, who made them and what still needs them. Every blob has a long random name nobody can guess. All app windows share their blobs; each outside tool (MCP, listener) only ever sees its own. A file attached to a draft, or to a message waiting to send, is never thrown away, not even when the window closes. Everything else is cleaned up when the window that made it closes, after a short timeout, or at the next start. Opening a received attachment downloads it once into the existing attachments cache and hands the window a blob for it. Nothing in this note lets a window open a received file inside the app with special powers: the window gets bytes and the sender's claimed type, nothing more.

## Decisions (safe default, then what would change it)

1. **Bytes live in host files, not engine memory.** Drafts survive restarts and point at blob ids, so the bytes must be durable; memory with a cap would lose a draft's attachments on every engine restart (the utility is killed and respawned). New host port `BlobFiles` in `packages/engine/src/ports/content.ts`, an additive optional `HostPorts.blobFiles` (absent stays the `unavailable` stand-in, so `Blob/*` answers "not running yet" exactly as today):
   `put(id, header, bytes): Promise<void>`, `get(id): Promise<{header, bytes} | undefined>`, `remove(id): Promise<void>` (idempotent), `list(): Promise<{id, header, mtimeMs}[]>`, `usage(): Promise<number>`. `header` = `{principal, kind: 'upload'|'original', mime, name?, size, createdAt}`. The engine never passes or receives a path. Implementation `apps/desktop/src/host/blobs.ts` (Node only), wired in `compose.ts` `engineOptions` next to `keys` from `options.dataDir`.
   - Layout: `<dataDir>/blobs/` (0700) holding `<id>.blob` (0600); temp files in `<dataDir>/blobs/.tmp/`. One file = a fixed magic line, one JSON header line (at most 2 KB), then the bytes, so header and bytes land in one atomic rename.
   - Write: `open(tmp, O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW, 0o600)`, write, `fsync`, `rename` to the final name (refused if it exists), best-effort directory `fsync`. Read: `open(O_RDONLY|O_NOFOLLOW)`, `fstat` must be a regular file with size <= 25 MB + header cap, else treated as gone.
   - Start: `lstat` the folder (must be a real directory, not a link; `chmod 0700`), empty `.tmp/`, ignore and delete names that do not match the id pattern.
   - Would change: a mobile host without a file system supplies an in-memory `BlobFiles` with the same contract (drafts then lose attachments on restart, which that host must say).
2. **Attachments reuse the store's attachment cache, not `BlobFiles`.** ARCH 3.3 already puts received attachments under `attachments/.noindex/` behind eng-store's `AttachmentFiles` port (designed, not yet implemented in `host/files.ts`). `Attachment/get` writes there and commits `attachmentState present`; its blob is an engine-side handle onto that cached file (kind `attachment`, in memory only, never a second copy). Would change: if store-5 retention never lands, a simple 1 GB LRU over `usage()` in the same PR.
3. **Handles.** `blobId = "b_" + 32 hex` from 16 bytes of `services.randomBytes` (128 bits, DECISIONS' condition), checked by `/^b_[0-9a-f]{32}$/` in the engine AND again in the host before any path is formed. Principal from `principalOf(caller)` stored in the header; a blob of another principal is `notFound` with the same sentence as an unknown id ("This file is no longer available."), never `forbidden`. Windows and main are one principal `app` (FR-6, recorded as accepted); listener/MCP clients are `client:<id>`, never `app`.
4. **Caps.** Per put 25 MB of bytes (contract; the transport's 26 MB is that plus envelope). Per principal: `app` 512 MB and 500 live blobs, each `client:<id>` 100 MB and 50; the whole folder 2 GB; and the host refuses a put when free disk is under 1 GB. Over a cap: `tooLarge` "Aplos is holding too many files. Send or remove some attachments first." Uploads attached to drafts count against the cap (the draft's own 30-file, 25 MB rule bounds one draft). Would change: the owner wants bigger sends (needs Gmail resumable upload, already planned in ARCH 7.1).
5. **`Blob/put`** (scope `draft`, `uploadRoutes`): the window posts `{bytes, mime, name}` with the buffer transferred (preload already does). Engine: size check, mime cleaned to a `type/subtype` token else `application/octet-stream`, name cleaned (no `/`, `\`, NUL, control chars, at most 255), id minted, `await blobFiles.put`, then registered in the in-memory index with `creator = ctx.connectionId`. Returns `{blobId, size}`.
6. **`Blob/get`** (scope `read`, `blobRoutes`): one reply with the whole file (at most 25 MB fits the 26 MB exemption). No chunking in v1: the window needs bytes only for in-app previews and dictation; saving and opening go through main's `File/save`/`File/open`, which call `Blob/get` on main's control connection (add it to `controlMethods`) so 25 MB never has to sit in a renderer to be saved. `port.ts` transfers the reply's buffer instead of copying it; the engine hands out a fresh buffer per call so the transfer can never detach a cached one. Would change: attachments over 25 MB (then an additive `offset/length` input).
7. **`Blob/release`** (scope `read`): own blob else `notFound`; referenced by a draft with a live submission (queued, scheduled, sending, uncertain, suspended, failed: the fixture's `live` set) `stateMismatch` "This file is attached to a message waiting to send."; otherwise drop from the index synchronously, then `remove` the file. A release of a blob a draft still references (no live send) is allowed, as in the fixture (the send then says "Attach it again").
8. **Lifecycle.** The index is rebuilt from `list()` at `start`. A blob is **held** while any draft row's `fields.attachments[].blobId` names it (one store read over `drafts`; a live submission is a draft reference too, so FR-7 holds even after the draft is edited). Held blobs are never released by a sweep, a timeout or a disconnect. Unheld blobs go: (a) `onConnectionClose(connectionId)` releases the ones that connection created (the window's state is gone, so nobody can still name them); (b) a sweep every 10 minutes on the timer loop drops unheld `upload` blobs older than 24 h and `original`/`attachment` handles 30 min after their last read; (c) at start, unheld `original` files go at once and unheld `upload` files older than 24 h go (a window that survived an engine restart keeps its fresh uploads). When the last draft reference goes (draft sent and settled, or destroyed) the blob becomes unheld and the 24 h rule ends it; no extra hook in the outbox.
9. **TOCTOU.** All index changes and the held check are synchronous inside one engine turn; the file delete only follows the index removal, so no call can see a blob that is half released. The outbox reads bytes asynchronously before it builds MIME (decision 10), and its commit already compares the draft revision (`SubmissionConflict draftRevision`), so a draft edited during the read loses cleanly. `Draft/set` checks every new `blobId` is in the index and owned by the caller's principal (else `notFound` "Attach it again"), so a listener cannot attach a window's file by id.
10. **Outbox reads.** `BlobSource.get` becomes `Promise<Uint8Array | undefined>`; `prepareSend` and `syncDraft` await `blobs.load(ids)` (at most the draft's 25 MB) and then build MIME synchronously from the map. The runtime gives the outbox a `BlobSource` that ignores principal (the draft's own attachments, checked at `Draft/set`). This also closes the DECISIONS gap "the production module has no `blobs` service".
11. **`Attachment/get`** (scope `read`): `messageId` = `<accountScope>:<remoteId>`, `attachmentId` = `attachments.remote_part` (`mail/rows.ts`). If the row is `present` and `AttachmentFiles.read(path)` gives bytes, hand out a handle. Else commit `fetching`, stream `services.accounts.attachment` with `collectBytes` under a **25 MB** cap (separate from the 10 MB cid image cap, which stays for `Mail/serve`) and a 120 s total / 30 s idle deadline tied to `ctx.signal` (a closed window cancels it), write, commit `present` with the path. One in-flight fetch per part (deduped), 3 per account. Over 25 MB: `tooLarge` "This attachment is too large to open in Aplos." No progress frames in v1 (query; the reader shows a spinner). The authenticated-From is irrelevant here: anyone with `read` may read any stored message's parts, as with bodies. Returned `mime` is the sender's declared type, cleaned; it is never used to decide anything.
12. **Content type is never trusted.** The engine does not sniff. The renderer previews in-app only images whose first bytes it checks itself (PNG, JPEG, GIF, WebP) through `URL.createObjectURL` in an `<img>`; HTML, SVG, PDF and everything else are save/open only. `File/open` (main) sniffs again and opens only its safe list. "Show original" is shown as text (`textContent`), never parsed as HTML.
13. **`Message/original`** (scope `read`): the provider's raw RFC822, fetched live (ARCH 3.3), through a new additive `ProviderPort.original(account, remoteMessageId): Promise<AsyncIterable<Uint8Array>>` (Gmail `messages.get format=raw`, priced as `full`; base64url decoded in the adapter), capped at 25 MB, stored as an `original` blob (`message/rfc822`, name = cleaned subject + `.eml`). Until the adapter exists the handler answers `unavailable`.
14. **Bundle.** Engine today about 410.6 KB of 450,000 B. Estimates (minified): `runtime/blobs.ts` index, caps, sweep and held check 3.5 KB; `methods/blob.ts` 1.2 KB; `Attachment/get` + `Message/original` 2.5 KB; outbox async read and `Draft/set` check 0.5 KB; port types 0. About 8 KB, so about 419 KB. Host-only and never in the engine bundle: every `node:fs`/`node:path` line, atomic write, folder checks, start cleanup, the Gmail raw decode, `File/save`/`File/open` and its sniffing.

## Security review points

- Path traversal: ids are validated twice; the host builds paths only as `join(blobsDir, id + '.blob')` and never accepts a path from the engine (`AttachmentFiles` keeps the store's `safePath`). Symlinks: `O_NOFOLLOW` on every open, `lstat` of the folder at start, `O_EXCL` temp files in our own 0700 folder.
- Quota exhaustion: per-put, per-principal, folder and free-disk caps; port.ts in-flight byte budget (64 MB) already bounds concurrent uploads; held blobs count, so an attacker with `draft` scope fills at most its own 100 MB.
- Handle guessing: 128 random bits; unknown and foreign ids answer identically. Cross-principal: every `Blob/*`, `Draft/set` and `File/*` path resolves through `principalOf`; a mutation test for each.
- Path leaks: no blob path, folder name or file error text in any reply, frame or log (log `reason` codes only); `File/save` returns only the path the owner picked.
- The accepted `app`-principal risk stands with its three conditions (DECISIONS); revisit before any lower-trust window gets a port.

## Test plan

- Engine (`packages/engine/tests/blob/*.test.ts`, in-memory `BlobFiles`): put/get/release round trip; caps; foreign principal `notFound` same sentence; release of a live-send attachment `stateMismatch`; held blob survives `onConnectionClose`, sweep and restart; unheld upload goes on close; 24 h and 30 min sweeps with the fake clock; `Draft/set` refuses a foreign or unknown blob; send reads bytes asynchronously and a draft edited mid-read conflicts; `Attachment/get` cache hit, fetch, dedupe, 25 MB cap, cancel on signal; `Message/original` cap and `unavailable` without the adapter.
- Host (`apps/desktop/tests/eng-contract/blobs.test.ts`, real temp dir): 0700/0600 modes, atomic write (kill between write and rename leaves only `.tmp`, cleaned at start), symlinked file and symlinked folder refused, bad id refused before any fs call, size over cap on read treated as gone.
- Mutation checks (each red, then restored): drop the principal compare; drop the held check in release; drop the held check in the sweep; release on disconnect regardless of held; skip `O_NOFOLLOW`; skip the host id check; reuse the cached buffer in the transferred reply; remove the 25 MB attachment cap.
- Headless real path: one `APLOS_TEST=1 APLOS_ENGINE=real` launch of the built app with isolated storage: a hidden window `Blob/put`s 5 MB, `Draft/set` attaches it, `SIGKILL` the engine process, after reconnect `Blob/get` returns the same bytes and the draft still sends into a fake `SendPort` with them; a second window reads the blob (same principal); closing the first window keeps it; a listener caller gets `notFound`. No real mail is sent.
