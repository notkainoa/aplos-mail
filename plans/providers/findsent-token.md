# Gmail `findSent` without our Message-ID: the `X-Aplos-Send` token

Written 2026-11-05 by providers-3, design first, after the Integrator's live send result (`gmail.send-message-id`: Gmail rewrites the Message-ID on `messages.send`, a custom header survives on the Sent copy, `rfc822msgid:` search finds the mail only under Gmail's id and only after about four tries, a few seconds late).

> **In plain words.** When the app sends mail and dies before it hears the answer, it later asks Gmail "did this go out?" (`findSent`). It used to ask by the mail's own id, which Gmail now replaces, so the answer could never be "yes". The fix: the adapter stamps every message it sends with a private random label in a header Gmail keeps, and later looks for that label in Sent. If it finds the mail, the send is confirmed and nothing is sent again. If not, it says "not found" only after looking a few seconds more (Gmail's index is slow) and, as before, an unclear send is never retried by itself: the owner decides.

## Decisions (defaults I will build unless engine or the Integrator objects)

1. **Where the token is written: the Gmail adapter, at send time. No engine change.** `transmit` uploads the engine's pinned MIME with one extra first header `X-Aplos-Send: <payload.internetId>`, exactly as drafts carry `X-Aplos-Draft` (`draft-token.ts`). The pinned bytes stay the engine's own: `pinnedMime` and its header allow-list (`PINNED_HEADERS`) still REFUSE an `X-Aplos-Send` (or `X-Aplos-Draft`) inside the pinned bytes, so a token never comes from outside. The token is the submission's own Message-ID value (`<random@domain>`, stable per submission, never regenerated), so retries of one submission carry the same token and different submissions never share one. It is random, reveals nothing, and is visible to recipients under "Show original"; recorded in DECISIONS.
2. **`findSent(internetId, since)` accepts a Sent copy by token OR by Message-ID.** A candidate is a message with the SENT label, no DRAFT label, and either `X-Aplos-Send` equal to `internetId` or (accounts that keep the id, older mail) a Message-ID equal to it. Candidates come from the two existing paths, both read with metadata `['Message-ID','X-Aplos-Send']`: the `rfc822msgid:` search (finds a copy under our id where Gmail kept it) and the SENT-label listing, newest first, which is not search-backed and is the path that finds a copy by token (`recentSentCopy`, at most 10 per page, 3 pages, at most about 600 units). The header only FINDS the candidate; the proof stays: SENT and not DRAFT, the token (a random 128-bit-style value only we wrote), and the existing time window (`since`, with the same slack and margin as today).
3. **Index lag: one pass, the engine's own re-check covers it (revised while building).** The note first proposed up to 3 more looks 3 s apart inside `findSent`. Not built: the engine already asks again after 60 s before it asks the owner (engine.ts: "findSent, once more after 60 s, then ask the user"), which covers the few-seconds lag measured live (the 4th try, about 3 s apart); and a sleep inside the adapter call stalls the engine's dispatch (it made the Gmail kill-point matrix, child processes on a fake clock, stop settling). `findSent` makes one pass; an error in it is thrown, never "absent". If the engine's re-check cadence ever changes, revisit.
4. **Unchanged:** an uncertain send is never retried automatically; `useDraftsSend` stays OFF (both routes upload the pinned bytes; the token is added by `transmit` only for the `messages.send` route that carries the bytes); the gone-draft check in `chooseRoute` uses the same lookup, so it also finds a copy by token.
5. **Not covered, by design:** mail sent before this change has no token and Gmail replaced its id, so it can only come back as "unknown" (the owner decides); mail sent from another device never carries the token (the engine only asks about its own submissions).

## Tests (emulator `sendIdentity: 'rewritten'` keeps custom headers like the live result)

Token on the wire exactly once as the first header and the pinned bytes otherwise unchanged; a pinned MIME that carries `X-Aplos-Send` is refused; `findSent` finds a rewritten-id copy by token (found), never one without the token, never a copy that is a DRAFT or lacks SENT, never a copy whose token belongs to another submission; a copy the index shows only later is absent now and found by the next ask; no sleeping inside the call; an error in the pass is thrown; mutations: token not written, token ignored, Message-ID-only match, no label check, duplicate header counted.
