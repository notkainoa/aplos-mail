# Council answer: Aplos Mail vs Inbox Zero

*Read of the four reports plus direct spot-checks in both codebases, 2026-10-25. Claims verified in source cite the path. Disagreements are in section 8.*

## 1. Verdict

Aplos Mail is a two-week-old, single-developer macOS prototype whose core loop has never worked against a real mailbox: the only live Gmail attempt failed with a 403 and the fix (v0.2.3) is untested, so "it syncs your email" is a hypothesis, not a feature. Inbox Zero is a three-year, ~90-contributor, 12.8k-star product with a deep server-side automation engine, a real eval harness, and a client that shipped a week ago on web, Mac, Windows and iPhone. On capability Aplos trails on nearly every axis: rules, reply tracking, cold-email blocking, bulk unsubscribe, snooze, send-later, drafts that live outside one laptop, mobile, and automation while the machine sleeps. Its real edges are protocol breadth (IMAP/JMAP/CalDAV, where Inbox Zero has refused IMAP since Dec 2023), local-first privacy with bring-your-own or local models, and native desktop craft, but every edge is unproven and two of the three are website claims the code cannot honour. Most decisively, Aplos is not yet a product: the repository is private, so the Download button and auto-updater 404 for everyone and all four releases are unpublished drafts; Inbox Zero is a company with a product, and Aplos is a promising prototype with a distribution problem, an unverified core loop, and a scale ceiling on the user's own laptop.

## 3. Architecture: local-first desktop vs server SaaS

**Where the server is fundamentally advantaged.** Inbox Zero acts on mail the instant it arrives, because Pub/Sub and Graph subscriptions push to a server that is always awake. That is the whole basis of "the work happens before you show up": rules fire, cold email is blocked, drafts are written, nudges go out while the laptop is closed. Aplos structurally cannot do this. It polls every 60 s (`service.ts:958-959`), disables IMAP IDLE (`imap-session.ts:71`), implements no JMAP push, and creates no Gmail server-side filters. Nothing Aplos automates happens unless the app is running; only a backend or the provider's own filter engine fixes that.

**Where the server is capped.** Inbox Zero's push path is also its fragility. Webhooks run rules, LLM calls and categorisation inline in `after()` with no queue, backpressure or per-account serialization, so a mail burst becomes a concurrent LLM and Gmail burst. Pub/Sub auth is a plain `!==` on a query token with no OIDC check, and hourly `watch` renewal re-watches every premium account serially inside one function.

**The quota irony.** Both share the same Gmail first-sync weakness, and Inbox Zero's live path is arguably worse: the client bootstraps the whole mailbox at `pageSize: 50` and the server runs `Promise.all` over every ID with `format=full`, a 50-way fan-out, and any provider error returns `paused` with `retryAfterMs: 1000`, so a 403 is retried a second later with another 50-way fan-out. The correct design already sits unused in their repo: `local-mail-sync-budget.ts` is a Redis token bucket in Gmail quota units with one in-flight request per account. Aplos does 500 × `threads.get?format=full` at concurrency 4, all-or-nothing, with no shared pacing, batch endpoint, `fields` mask, or sibling cancellation.

**Multi-device is the ugly one.** Aplos syncs Done/Later/todo/due-date as a last-writer-wins log sealed with AES-256-GCM, written as a hidden Gmail message under an "Aplos Mail Data" label, then trashed after each merge. The merge is commutative and idempotent, which is careful work. But conflicts are decided by device clocks, the Trash fills with sync-data messages that count against storage, and only workflow state syncs: drafts, settings, AI keys, Ask history and summaries do not, so summaries are re-paid per device.

**Privacy, honestly.** "No Aplos server ever sees your mail" is true; the AI provider still does, by default Groq, for every summarised thread. Mail at rest in `aplos.db` is unencrypted, protected only by FileVault. Cross-device sync writes workflow state into your Gmail account. The defensible claim is "your mail goes only where you choose."

**Verification burden.** Both request `gmail.modify` (Aplos also `gmail.settings.basic`), both restricted, so both need verification and a CASA assessment; serverless does not exempt Aplos, and sending content to third-party LLM APIs by default makes a Limited Use disclosure hard to avoid. Inbox Zero has a company and public SOC 2 and CASA claims; Aplos has a Testing-status app with a 100-test-user cap and 7-day refresh tokens.

**Strategic read.** The architectures converge from opposite directions. Inbox Zero now ships a local SQLite engine in an Electron utility process while keeping the server for automation; Aplos has the local engine and no automation plane. Inbox Zero can add local-first, but Aplos cannot easily add a 24/7 automation plane without becoming a hosted service. That asymmetry is the most important strategic fact here.

## 4. Ten weaknesses, ranked

1. **Nothing is downloadable.** Private repo, so `/releases/latest` and `latest-mac.yml` 404 and the updater (no token set) cannot work. *Fix:* publish the v0.2.3 draft from a public repo, repoint `releasesUrl`. *Hours.*
2. **The core loop was never verified live.** No provider has synced a real mailbox. *Fix:* handle `invalid_grant` and missing scopes with a Reconnect CTA, then dogfood on the owner's inbox for two weeks. *Days to weeks.*
3. **Gmail first sync is all-or-nothing and unpaced.** No shared limiter, batch, `fields` mask or checkpoint; siblings keep spending quota after a failure; retries restart from zero. *Fix:* quota-unit token bucket (~150-200 units/s), metadata-first, lazy bodies, page-level commits, sibling cancellation, ~100-thread window. *1-2 weeks.*
4. **The whole mailbox is an in-memory document.** `load()` parses everything, `change()` clones the mailbox per mutation, `save()` re-stringifies every thread per commit, FTS `DELETE` hits an `UNINDEXED` column, and most methods return `clone(state)` over two IPC hops with no eviction or cache cap. *Fix:* load on demand, page the renderer, evict bodies, cap the cache, fix the FTS delete. *2-4 weeks.*
5. **Google OAuth verification.** Two restricted scopes, Testing status, 7-day refresh tokens, third-party LLM transfer. *Fix:* drop `gmail.settings.basic` if aliases can wait, go to production, start verification and CASA, publish a privacy policy naming providers and the Limited Use commitment. *Weeks plus external review.*
6. **Untrusted HTML in the privileged renderer.** Sanitized HTML is re-serialized, re-parsed and injected with `dangerouslySetInnerHTML` into the document holding `window.aplos`, with `script-src 'unsafe-inline'`; one mXSS bypass yields send, export and settings. Fuses are unconfigured (RunAsNode on). *Fix:* opaque-origin sandboxed iframe, tighter CSP, fuses, narrower entitlements, then re-enable styles so newsletters render. *3-7 days.*
7. **No observability.** ~6 `console.*` calls, no crash reporter, log or diagnostics bundle; the 403 cost a release just to read Google's reason. *Fix:* `crashReporter.start`, rotating log, redacted diagnostics, per-account Connection report. *1-2 days.*
8. **Not yet a daily driver.** Drafts are local-only (no `drafts.*` in `google.ts`; verified), so a draft is invisible on the phone. No rules, snooze verb, send-later, contacts or label management, and unsubscribe ignores the `List-Unsubscribe` header already in the payload. *Fix in order:* Gmail draft sync, one-click unsubscribe, snooze and send-later, block-sender creates a real Gmail filter, then a local rules slice. *2-3 weeks for the first four.*
9. **Cross-device sync pollutes the mailbox.** Hidden messages trashed after each merge, clock-based conflicts, workflow state only. *Fix:* smaller payload and stop trashing, or drop to settings-only and say so; a real fix needs an optional relay. *1 week to improve, months for the real fix.*
10. **Maintainability.** Minified-with-comments code (733 lines over 200 chars), no formatter or linter, a ~770-line god-closure in `service.ts`, the IPC allowlist copied in three places, pre-stable `node:sqlite`. *Fix:* Biome, split `service.ts`, one typed IPC contract, a renderer smoke test. *1 week, mostly mechanical.*

## 5. Where Aplos can genuinely win

- **Protocol breadth for non-Google mail.** Inbox Zero has refused IMAP/SMTP since Dec 2023 (#62, #925) and supports only Gmail and Outlook, so every iCloud, Fastmail, self-hosted and corporate-IMAP user is unserved by both Inbox Zero and Superhuman. This is the clearest market gap and the one claim Aplos makes that the incumbent cannot answer without a rewrite. It is worthless until one non-Gmail path is verified live, and each protocol is a permanent maintenance tax.
- **Local-first with a real privacy boundary.** "Mail stays on your Mac and you choose the model" is genuine and not free for a hosted product to copy. It also makes marginal cost zero, the only reason a free tier is sustainable. The caveat stands: the claim is about control, not about no third party ever seeing mail.
- **A real calendar in the same app.** Inbox Zero's calendar serves automation; Aplos's is a client with drag-to-create, resize, CalDAV and multiple accounts. A different, real product, currently weak (no recurrence, RSVP or conference links, Google invites suppressed).

**Weak or overstated claims.** "Works with Gmail, Outlook, iCloud, Fastmail and any IMAP account" is false today, since Outlook cannot sign in at all (no `MICROSOFT_CLIENT_ID`) and nothing non-Gmail has run live. "No Aplos server ever sees your mail" is true but misleading while Groq sees every summarised thread by default. "Fast, keyboard-first" is unverified on real mail, and the whole Home experience depends on an importance pass proven only on demo data. Native craft is a two-week edge, not a moat, and Windows and Linux are marketing. The honest wedge is therefore narrow: **the privacy-native, multi-protocol, keyboard-first client for people whose mail is not on Gmail.** Small, real, addressable, and the opposite of where the marketing points.

## 6. What to learn from Inbox Zero

Ideas and patterns only. Their license is AGPL-3.0 plus a clause requiring an enterprise license for five or more business users, so read for architecture and copy nothing.

- **The quota-unit token bucket:** budget in quota units not requests, one in-flight per account, read `historyId` before backfilling, `retry:false` so only one retry layer exists, sequential hydration, slow refill after a throttle.
- **Rate-limit classification:** key off Gmail's `reason`, parse "Retry after `<timestamp>`" from the message text, treat daily `quotaExceeded` as stop-for-today, default the cooldown to 30-60 s when Google gives no time (their ~1 s fallback is a bug), add jitter, and fail fast and reschedule instead of sleeping.
- **Test / history / fix, plus learned patterns:** run rules against past mail without executing, let a user explain a wrong match so the rule updates, and keep editable per-sender patterns. Applied to importance classification, this also blunts the prompt-injection risk of a malicious email steering Home ordering. Match deterministically first (static, learned-pattern and thread-continuity passes) before spending an LLM call, which is both cheaper and the right shape for Aplos's eventual local rules.
- **Eval and emulator discipline:** fixed corpus, multi-model matrix, LLM-as-judge, ablations, and provider flows driven against an emulator stack. Aplos has fake servers but no packaged E2E. Beat them by gating CI on the evals, since their AI evals are manual-only.
- **Anti-patterns to avoid:** four overlapping cleanup flows, ~20 feature flags mostly off by default, 102 Prisma models, four queue backends, deprecated columns. Do not chase breadth. Note also their safety regression: removing the approval flow means rule actions now send, forward and call webhooks unconfirmed. Aplos's confirm cards are better; keep them.

## 7. Ranked 30-day plan

1. **Days 0-2 — make it downloadable.** Publish the v0.2.3 draft from a public repo, fix `releasesUrl` and the updater, install on a clean second Mac, confirm Gatekeeper and a full auto-update. Ship a macOS-only download page.
2. **Days 2-4 — observability first.** Crash reporter, rotating file log, redacted diagnostics bundle, per-account Connection report (scopes granted, token expiry, last error, quota state). You cannot debug the 403 blind.
3. **Days 3-8 — make the first Gmail sync survive a real mailbox.** Token bucket, metadata-first with a `fields` mask, lazy bodies, checkpointed page commits, sibling cancellation, ~100-thread window, explicit `invalid_grant` handling with a Reconnect CTA. Verify on the owner's inbox, then on a deliberately large one.
4. **Days 5-14 — dogfood.** Make it the default mail app and fix what breaks. This is the only thing that converts "build" into "ship" in the table above.
5. **Days 8-12 — sandbox the email HTML** in an opaque-origin iframe, tighten CSP, add fuses, narrow entitlements, then re-enable styles so newsletters render. Biggest security gap and a rendering win at once.
6. **Days 10-16 — fix the store.** Stop returning `clone(state)`, load threads on demand, page the renderer, evict bodies, cap the cache, fix the FTS delete. Target: a 50k-thread mailbox opens in under two seconds and stays under ~400MB.
7. **Days 12-20 — daily-driver gaps, in order:** Gmail draft sync, one-click `List-Unsubscribe`, snooze as a first-class verb, send-later, block-sender creates a real Gmail filter, then a deterministic-first local rules slice that runs while the app is open.
8. **Days 15-24 — Google OAuth production readiness.** Drop `gmail.settings.basic` if aliases can wait, submit for verification, start CASA, publish a privacy policy naming the AI providers and the Limited Use commitment, add a scope check on the token response. In parallel commit to IMAP-first, because app-password auth needs no verification.
9. **Days 20-27 — make the provider claims true.** Either add `MICROSOFT_CLIENT_ID` and verify a real Graph account, or remove Outlook from the site. Verify one live IMAP account and one live CalDAV calendar. Reconcile every website claim with reality.
10. **Days 24-30 — quality gates.** Biome with a formatter, split `service.ts`, one typed IPC contract, a packaged E2E against emulated providers in CI, and `eval:groq` as a CI gate on a fixed synthetic corpus.

Success at 30 days is not parity. It is: a stranger downloads a signed build, connects a real Gmail or IMAP account, syncs a 10k-thread mailbox without a 403, uses it for a week without losing a send or a draft, and updates it in place.

## 8. Disagreements with the reports

- **Both Aplos reports are wrong about signing.** The architecture report says no release is signed and every build is ad-hoc signed, so auto-update is off for everyone. The verified facts say 0.2.0-0.2.3 are Developer ID signed and notarized. They are unpublished drafts, and the updater is dead because the repo is private, not because the builds are unsigned. That matters: the remaining distribution work is *publishing*, measured in hours, not *signing*.
- **Observability is under-ranked.** It is the fourth of four summary weaknesses; it belongs in the top three, because it is why one 403 consumed a release cycle.
- **"CASA is probably unavoidable" is slightly too fatal.** True for the default configuration where Groq sees every thread, but the app already supports Ollama and LM Studio, so the burden is a function of the *default*, which is a product decision. A local-first default changes the story.
- **The `reset` bug is real but overstated, and the renderer-paging claim implies a rewrite it is not.** I confirmed `freshWindow` returns `reset: true` (`google.ts`) and that `service.ts`/`merge.ts` never read it, but on a first sync there is nothing stale to reconcile, and mail outside the window is never reconciled anyway, so it bites the long tail. Similarly, `threads.page` already exists as an engine method, so the renderer loading everything is a wiring change plus on-demand loading, not a dead end.
- **The product report misses that the AI will claim to snooze.** It correctly notes there is no snooze verb, but `triageLabel` in `writer.ts` accepts "snooze" as an alias for Later and `ask.ts` advertises snoozing in `propose_triage`. The assistant will tell a user it snoozed something that has no such state: a small trust bug in the one surface trying to feel clever.
- **Both reports undersell the licensing asymmetry.** Inbox Zero is AGPL with a commercial-use cap at five users, so source-available rather than open. For a genuinely local, permissively licensed competitor that is an opening, and more interesting than the SOC 2 question. The product report also treats the stale Reply Zero docs as a live inconsistency, but the architecture report shows the standalone page was removed and it is now system rules behind a `follow-up-reminders` flag.
- **The product report omits the one place Aplos is not behind.** Inbox Zero's live first-sync path is as broken as Aplos's: a 50-way `messages.get` fan-out with a ~1-second retry on any provider error, with a correct token bucket sitting unused in the repo. The architecture report flags it, and it is the strongest evidence that Aplos's Gmail problem is a known, solvable pattern.
