# Council verdict: Aplos Mail vs Inbox Zero

Written 2026-10-25 from the four input reports plus the verified facts (which override the reports where they conflict). I am deliberately critical rather than balanced.

## 1. Verdict in five sentences

Aplos is not competing with Inbox Zero today; it is a well-engineered two-week-old prototype whose single documented encounter with a real mailbox ended in a Google 403, while Inbox Zero is a three-year-old product with 12.8k stars, ~90 contributors, a hosted SaaS with paying tiers, a self-hosting story, and a brand-new free desktop/iPhone client shipped on 2026-10-18. Aplos cannot even be downloaded by anyone but the owner right now: the repo is private, all four releases are drafts, the site's Download button and the electron-updater feed 404 publicly, and Microsoft sign-in is missing entirely because no client ID exists. What Aplos has that Inbox Zero structurally lacks — true local-first privacy, BYO/local AI, IMAP/JMAP/CalDAV, a real calendar, no server holding your tokens — is genuinely valuable but is currently resting on code that has never synced a single real message and has no logging, so any field failure is invisible. Inbox Zero's counterweights are a server that sees every user's mail, restricted-scope CASA burden, an AGPL-plus-commercial-restrictions license, Gmail/Outlook-only providers, and a first-sync path with the same quota-fragility Aplos just hit. Honest bottom line: Aplos is roughly where Inbox Zero was in month one, except pre-launch, single-platform, unverified, and unobservable — the ideas are competitive, the product is not yet.

## 3. Architecture: local-first desktop vs server SaaS

**Where each design is fundamentally advantaged.**

Aplos's local-first design wins on **privacy** (mail and tokens stay on the Mac; AI can be fully local via Ollama/LM Studio; no server blast radius, no SOC 2 / subprocessor list needed), **cost** (no per-user server, no LLM spend for the developer), **latency and offline use**, and **protocol breadth** (IMAP/JMAP/CalDAV are only practical client-side; Inbox Zero may never do IMAP well server-side). Its sending guarantees (stable Message-ID, findSent reconciliation, never auto-resend) are also better than Inbox Zero's, whose rule REPLY/SEND/FORWARD actions execute automatically with no approval step since the approval flow was removed.

Inbox Zero's server design wins on everything that requires a process that never sleeps: **push** (Pub/Sub and Graph webhooks vs Aplos's 60 s polling), **rules and cold-email blocking that run while the laptop is closed**, **scheduled send and follow-up nudges with the Mac off**, **web/mobile clients that don't each re-sync the whole mailbox**, and **whole-mailbox features** (bulk unsubscribe over years of history, analytics) — Aplos only ever sees a 500-thread window plus new mail, which structurally caps those features forever. It also centralizes evals, spend accounting and telemetry, so the developer can actually see failures.

**Verification burden is the sharpest asymmetry.** Both request restricted Gmail scopes (`gmail.modify`), so both owe Google a CASA assessment and Limited Use compliance. But Inbox Zero has already paid it down (claims CASA Tier 2, verified app, SOC 2 posture) while Aplos sits in "Testing": max 100 test users, 7-day refresh tokens forcing weekly reconnects, unverified-app warnings, and `invalid_grant` not even surfaced as "reconnect" in the code. Worse, Aplos's default Groq path sends message content to a third-party LLM, which undermines the "data stays on device" argument Google historically rewarded with leniency. And unlike Inbox Zero, Aplos has no server to hide behind — its bundled desktop client secret is extractable and shares one project quota across all users.

**Scale cuts both ways.** Inbox Zero's monolith has 102 Prisma models, four queue backends, and a first-sync path that fans out 50 parallel `messages.get` calls with a ~1 s retry — the same disease as Aplos's 500-thread concurrency-4 all-or-nothing sync, in a product with real users. Aplos's mailbox-as-one-JSON-blob (cloned and re-serialized per mutation, ~4 in-memory copies, 10k threads = 1 GB renderer) is a harder ceiling: it caps the product at small mailboxes even on fast hardware. Neither architecture is capped by its paradigm; both are capped by current implementation. But Inbox Zero's cap is operational sprawl, fixable incrementally by a funded team; Aplos's cap means the core data model needs a rewrite before the product can serve its most email-burdened (i.e., best-paying) users.

## 4. Aplos's 10 most serious weaknesses vs Inbox Zero, ranked

1. **Nobody can download it.** Repo private, releases unpublished drafts, Download button and `latest-mac.yml` 404 publicly, and electron-updater has no token for a private repo. Fix: make the repo (or at least releases) public and publish v0.2.3. Effort: an afternoon, plus a decision. This dwarfs everything below.
2. **No real mailbox has ever synced.** The one live Gmail attempt (0.2.2) failed with a 403; the 0.2.3 retry fix is untested by anyone. Every feature maturity label above is "mocks only". Fix: dogfood daily on the owner's real accounts, add live-provider smoke tests (M11). Effort: days of testing plus iterating on real failures.
3. **The first sync is all-or-nothing, unpaced, and inline with AI.** 500 threads, `format=full`, concurrency 4, no shared token bucket, no batch, no `fields` mask, no checkpoint/cancellation; plus up to 500 LLM summaries awaited inside the sync path, with serial account sync so one Groq free-tier 429 stalls everything. This is the direct cause of the 403. Fix: quota-unit token bucket (~150-200 units/s), batch `messages.get` with `format=metadata` + lazy bodies, commit per page with a cursor, move classification off the critical path. Effort: 1-2 weeks.
4. **Google verification is a distribution blocker.** Testing mode = 100 users, 7-day refresh tokens, warning screens; restricted scopes need CASA; `invalid_grant` and granted-scope mismatches aren't handled. Fix: handle `invalid_grant` → reconnect, check the token's `scope` field, drop `gmail.settings.basic`, start verification early. Effort: code days; CASA is weeks-to-months and costs money.
5. **Zero observability.** No log file, no crash reporter; the 403 needed a whole new release just to see Google's reason. Fix: local rotating log with redaction, `crashReporter`, a "copy diagnostics" button. Effort: 1-2 days; highest leverage per hour on this list.
6. **The data model won't scale.** One JSON blob per thread, full bodies + base64 attachments inline, `structuredClone` of the whole mailbox per mutation, whole-state IPC. Already failed at 10k threads. Fix: normalize bodies out of the thread row, load on demand, page IPC results, keep FTS but fix the `UNINDEXED` DELETE scan. Effort: 2-4 weeks, mostly mechanical.
7. **No automation surface at all.** Inbox Zero's core product — persistent rules, reply tracking, cold-email blocking — is absent, and the design can't run rules while the Mac sleeps. Fix: don't chase server rules; ship client-side rules (Gmail filters via API, local rule matching on sync) and be honest that it works "when your Mac is on". Effort: 2-3 weeks for a minimal rules MVP.
8. **Outlook is dead code.** No `MICROSOFT_CLIENT_ID`; the build literally says sign-in isn't available. Fix: register a public client, wire the secret, test on a real account. Effort: 1-2 days of setup, then live testing.
9. **Email HTML renders in the privileged renderer.** Sanitize→serialize→re-parse mutation-XSS shape, CSP `'unsafe-inline'`, no sandboxed iframe, no Electron fuses, broad entitlements — a DOMPurify bypass gets the full bridge. Fix: sandboxed `iframe srcdoc`, tighten CSP, set fuses. Effort: ~1 week.
10. **Unproven cross-device and calendar claims.** Workflow sync verified only against fake mailboxes; live calendars unverified; recurring events read-only; Gmail sync-data messages pile up in Trash. Fix: live test the sync pair, reconcile deletions on cursor `reset` (currently ignored, leaving ghost threads). Effort: ~1 week.

## 5. Where Aplos can genuinely win

Genuinely defensible, today or near-term:

- **Privacy as architecture, not policy.** "No Aplos server exists" is a claim Inbox Zero can never make; its own HN launch thread is full of users refusing to hand their inbox to a server plus OpenAI. For individuals who care, this is the whole purchase. It is defensible because it's structural.
- **Local AI.** Ollama/LM Studio routing per feature is something Inbox Zero only offers to self-hosters running their own server. Real niche, real users.
- **Provider breadth: IMAP, JMAP/Fastmail, iCloud, CalDAV.** Inbox Zero has ignored IMAP for three years (issues #62, #925). This is a durable wedge — everyone on Fastmail, Proton-adjacent, self-hosted, or iCloud is unserved by Inbox Zero. Currently weak because none of it is verified live; it becomes real the day a second person's Fastmail account syncs.
- **A real built-in calendar with editing.** Inbox Zero's calendar is booking/briefing-oriented, not a unified week view you drag events in. Combined with CalDAV, Aplos can be the only local client that does both well.
- **Trustworthy AI posture.** Read-only tools, ref-scoped citations, proposal-only actions, no sparkle icons. This is better-designed than Inbox Zero's auto-executing REPLY/SEND/FORWARD rules, and it's a marketable difference ("it never sends anything on its own").

Weak or wishful claims I'd call out: "Windows and Linux later" (site sample data, no code), Outlook support (no client ID), "works with your team" anything (none exists), and Home's "finish your inbox" experience, which is entirely dependent on an AI importance pass proven only on demo mail. The unified-calendar-plus-mail local client for the Mac is the credible wedge; the "Aplos for everyone" story is not yet.

## 6. What to learn or adopt from Inbox Zero (ideas and patterns only — never its AGPL code)

- **Dogfood publicly and let the repo be the changelog.** Inbox Zero's founder commits daily against his own mail; that is why his Gmail integration works. Aplos's gap between 228 green tests and one failed live sync is the exact lesson: fake servers verify invariants, not reality.
- **Quota-unit token bucketing** (their unused `local-mail-sync-budget.ts` design is the right template, per their own audit): budget in Gmail quota units, one in-flight request per account, record `historyId` before backfill, `retry:false` on googleapis, sequential hydration. Adopt the pattern; their shipped code ironically doesn't.
- **Error classification by provider reason, not HTTP code**: parse Gmail's `Retry-After <timestamp>` text, distinguish `userRateLimitExceeded` from `quotaExceeded` (stop for the day) from `insufficientPermissions` (reconnect). Their AADSTS error table for Microsoft is also a good pattern.
- **The rules interaction model**: plain-English rule → review → save → test tab → history with "explain the mistake" feedback loop. Even a client-side subset of this beats having nothing.
- **Sender-level bulk operations** with read-rate heuristics and "select N suggested" —Aplos's local window can support this for the recent mailbox.
- **Eval discipline**: their 72-file eval harness with LLM-as-judge, even manually run, exceeds Aplos's 8-case corpus. Aplos needs a CI-gated eval set with regression history before tuning prompts against real mail.
- **Structural AI guardrails**: template-field-only AI fill (injected to/cc/bcc ignored), spoofable-from blocking on send actions. Aplos's ref-scoping is good; add these.
- **What not to adopt**: webhook-inline AI with no queue, four queue backends, hourly re-watch of every account, 102-model schema sprawl, prompts as inline strings with manual version integers, auto-executing outbound actions, and the "1000 landing pages" SEO strategy (no traffic to monetize yet).

## 7. Ranked 30-day plan

1. **Day 1-2: make it installable.** Publish the repo or releases, publish v0.2.3, fix the Download button, verify the updater feed works for an unauthenticated user, confirm Gatekeeper on a second Mac.
2. **Day 1-3: observability.** Rotating redacted log file, crashReporter, diagnostics bundle button. Everything after this depends on it.
3. **Day 3-7: fix the first sync for real.** Token-bucket pacing, batch + `fields` + `format=metadata` first pass, lazy bodies, per-page commits, abort siblings on failure, move `classifyIncoming` off the sync path (queue summaries in the background, degrade gracefully without a key). Then: owner syncs a real Gmail account and keeps it synced. This is the milestone that converts the project from prototype to product.
4. **Day 5-8: OAuth hardening.** Handle `invalid_grant` as reconnect, verify granted scopes, drop `gmail.settings.basic`, start the verification process (CASA will outlive the 30 days; start now).
5. **Day 7-10: Microsoft.** Register the public client, ship a build where Outlook sign-in works, test live.
6. **Day 10-14: live-test IMAP (Fastmail or iCloud) and one live calendar; honor cursor `reset` by reconciling deletions.** Two protocols verified live changes the public story from "claims" to "works".
7. **Day 12-16: security pass.** Sandbox email HTML in an `iframe srcdoc`, remove `'unsafe-inline'` and dev origins from prod CSP, configure Electron fuses, trim entitlements, add a pre-release `verify-release` gate in CI.
8. **Day 14-20: minimal rules.** "When mail arrives from/matches X → label/archive/mark read/draft" evaluated client-side on sync, with a test mode and history. Explicitly scoped to "runs when Aplos is open". Also: read `List-Unsubscribe` + RFC 8058 one-click (cheap, high visibility).
9. **Day 16-22: data-model triage.** Split bodies out of the thread JSON, on-demand body loads, bounded IPC payloads, a realistic scale test (1 MB bodies, not 160 chars). Target: 10k threads usable.
10. **Day 20-25: run the formatter** (Biome/Prettier), generate the shared typed IPC contract to replace the three copied allowlists, add one renderer E2E smoke in CI.
11. **Day 25-30: first external users.** Publish the site for real, ship to a handful of testers (test users on the Google app), instrument nothing but collect the log bundles, publish v0.3 with a working update path. Success criterion: someone who is not the owner finishes their first sync and still has the app installed a week later.

Deferred past 30 days (on purpose): server-side push, scheduled send, meeting tools, Windows/Linux, mobile, team features, encryption at rest.

## 8. Disagreements with the reports

- **The Aplos architecture report is wrong about signing.** Verified directly: 0.2.0-0.2.3 are Developer ID signed, notarized, and stapled. Its "no release is signed yet" and "auto-update is disabled for everyone" framing is outdated. The real distribution problem is different and worse: the repo is private, so the feed 404s and updates can't reach anyone regardless of signatures.
- **The Aplos architecture report underweights the private-repo blocker.** It notes it as one of "two blockers the docs don't mention" (actually the product report notes it); given the verified 404s, I'd rank it the single largest obstacle to Aplos being a product at all, above every technical risk.
- **The Inbox Zero product report's "SOC 2" and "25,000+ professionals" should be treated as unverified marketing, more strongly than the report's [C] hedging implies.** No public report, no named auditor, sign-ups conflated with users. In a comparison doc, these should carry no weight.
- **The Inbox Zero architecture report is too kind about its own repo's eval discipline relative to Aplos's.** It correctly notes evals aren't CI-gated, but "mature eval harness" overstates it: the draft eval cases load from a private dataset outside contributors can't reproduce, the matrix pins a model that differs from code defaults, and nothing gates releases. Aplos's 8-case corpus is far smaller, but neither product has release-gated AI quality; the gap is smaller than "72 eval files" suggests.
- **The Aplos product report's "first-sync AI cost" risk framing is right but understated in consequence.** Per the architecture audit, classification is awaited inside the global sync promise with serial accounts — so it doesn't just "slow" the first sync; on Groq free tier it can stall every account indefinitely. That's a correctness bug, not a cost concern.
- **Both Aplos reports praise the "engine is platform-free for a future mobile host" more than earned.** MOBILE.md is a portability spike with an empty `packages/`. Multi-device reality today is one Mac plus an encrypted hidden-message log. That's fine, but it shouldn't be counted as mobile groundwork.
- **One correction in Aplos's favor that the reports miss the significance of:** the send-safety design (stable Message-ID, unknown-outcome reconciliation, never auto-resend) is better than Inbox Zero's, whose automated REPLY/SEND/FORWARD rule actions execute with no approval step and whose Microsoft adapter discards rotated refresh tokens. If Aplos survives to be compared on engineering trust, that's a real line to draw.
