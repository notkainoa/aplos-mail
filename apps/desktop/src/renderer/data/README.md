## One vocabulary with the contract

Every type is the contract's. `contract-shapes.ts` re-exports `ThreadRow`, `Message`, `Draft`, `Submission`, `Account`, `Session`, `Settings`, `UiSettings`, `Consent`, `ViewSpec`, `WindowBody`, `WindowSection`, `ThreadAction`, `ThreadSelector`, `Receipt`, `State`, `Operation`, `ErrorBody`, `Frame` and the rest from `@aplos/contract` (types the contract exports only as zod schemas are inferred with `z.infer`). The thin aliases name what the contract leaves unnamed: `AccountId` and the other id aliases are `Id`, and `WindowFrame`, `StateFrame`, `ProgressFrame`, `ConnectFrame`, `ClockEvent`, `ParkedEvent` and `EngineEvent` are `Extract`s of `Frame`, `HostEvent` and `DesktopEvent`. Everything is type-only, so the surface costs the bundle no zod.

The hooks use the contract's names too: a window has `position` and `sections` (not `offset` and `groups`), state is `State` with its `seq`, errors are `ErrorBody`, a thread action is `{type: ...}`.

## The surface in plain words

**Lists are windows.** `useView(spec, {holdIds})` watches one view (`View/watch`). It returns the window as the contract shapes it: the ordered `ids` (at most 200), `position` (index of the first id), `total`, rows by id from the row cache, `sections` (Home sections, Later groups, Low senders), `held`, `rowType`, `state`, plus a `status` (`opening`, `live`, `reset`, `failed`), an `error` when it failed (`WindowBody.error`) and `move(range)`. The row type follows the spec: `thread` gives `Message`s, `drafts` gives `Draft`s, `scheduled` gives `Submission`s, `lowSenders` gives `SenderGroup`s, `events` gives `Event`s, `plans` gives `Plan`s, `conversations` gives `Conversation`s, and every other view gives `ThreadRow`s. The specs are the contract's 17 kinds, including `homeSection`, `oneByOne`, `mailbox` (by role) and `label` (by folder id) as two kinds, `done` for the Done place, and `search` with a structured `SearchQuery`.

**Home has a helper.** `useHome({accountId, holdIds})` turns the `home` window into what DESIGN 7.2 draws. The window's sections are `do`, `fromLater`, `update`, `low` and `follow`. Do now's count includes Back from Later, and `fromLater.count` is the block alone. A section emptied during a hold stays `visible` and shows 0 until the hold releases. `low` is count-only: the band's names come from its `senders`, and "and N more" from the `lowSenders` window's `total`. `state` is there so "Clear from Home" can send a selector `atState`.

**Rows are cached.** `useRow(type, id)` returns one row by contract type name (Thread, Message, Draft, Submission, Event, Plan, Conversation, SenderGroup, plus Account and Operation). It stays the same object while `rev` is unchanged. `useRowState` adds `loading`, `ready` or `notFound` (from `T/get`'s `notFound`).

**Commands act first.** `api.thread.act({ids | selector, action})` applies the optimistic overlay before it returns and gives `{opId, receipt}`. The data layer mints the `opId` when the caller gives none. A selector is `{spec, section?, atState}` over thread-row specs only (the type refuses the reader's message list). The overlay drops once a window's `state.seq` reaches `receipt.appliedState.seq` within one `dbEpoch`. `useOperation(opId)` reports `pending`, `confirmed` or `failed`, the provider-side `Operation.state`, `undoUntil`, and offers `retry()`. Undo is `api.operation.undo({opId})`, an inverse operation.

**Retry has two cases.** If the engine rejected the write, no operation exists: `RowFailure.retry()` and `OperationView.retry()` send a fresh `api.thread.act` with the same action and targets under a new `opId`, and the overlay re-applies at once. If the engine accepted the write and the provider later refused it (`Operation.state: 'failed'` after a receipt), `OperationView.retry()` calls `api.operation.retry({opId})` (`Operation/retry`). That keeps the same `opId`, returns a `Receipt` and applies no overlay.

**Search.** Local results come from `useView({kind: 'search', query})` as the owner types. Return calls `api.search.remote({query, accountId?})` (`Search/remote`), which answers at once with `{runId, receipt}`. Progress follows as `progress` frames with `source: 'search'` (`useFrames('progress', {runId})`), and the server's results join the open `search` window with the same query.

**Holding still, prefetch, bodies.** As before: `useHold(scope)` is the renderer half, `holdIds` the engine half (`View/hold`, repeated as the ping; `View/release`). There is one gate per list: `useHold(scope)` returns a `HoldGate` (the `HoldController` plus `pointerEnter(ids)` and `pointerLeave()`), the list passes its `heldIds` to `useView`, and gives the same object to the motion runtime's triage. The gate releases 450 ms after the last key, so a burst of any length closes once; the pointer leaving inside those 450 ms does not cut it short. With the pointer still on the list it waits for it to leave, but never past 1200 ms after the last key; then it closes once and, if the pointer is still there, goes straight on to a pointer-only hold of the row under the pointer, so the window stays frozen. A resting pointer holds until `pointerLeave()`; Esc closes and the resting pointer keeps holding its row. A hide releases and forgets the pointer (the list re-asserts it with `pointerEnter([hoveredId])` on the next pointermove). The list must name the row under the pointer: the engine only freezes a window whose `holdIds` are non-empty. With only the `HoldController` surface, `begin('pointer', ids)` holds until `release()`. `usePrefetchIntent()` sends `MessageBody/prefetch {threadIds}` after 80 ms focus or 120 ms hover and cancels with `{cancel: true}`. `useMessageBody(id)` loads one body and sets `slow` after 1.5 s.

**Session, status, counts, settings, consent.** `useSession()` is `Session/get`. `useConnection()` speaks the contract's `engine` vocabulary (`connecting`, `ready`, `unreachable`, `parked`; `ConnectionState` is the known values of that open enum, and a state a newer main adds is reported as `unreachable`) with `reason`, `reasonCode` and `canRetry`. `useAccounts()` returns `Account`s with `health`. `useStatus()` picks the one status line and gives its `reasonCode` (copy comes from the code, never from provider text). `useCounts()` gives the `CountsBlock` for the scope plus per-folder unread counts. `useAgenda({kind: 'events', from, to})` is an events window. `useSetupStatus()`, `useSettings()` and the new `useConsent()` read their singletons, re-read on `state` frames.

**Streams, clock, undo.** `useFrames('progress' | 'connect' | 'clock', filter)` serves the contract's `progress` and `connect` frames and the host clock event. A run is followed by the `runId` that `api.ask.run` returned, a connect flow by its `connectId`. `useNow`, `getNow`, `setClock` and the one undo stack are unchanged.

**Not here.** Transport selection (`renderer/bridge.ts` is the Electron MessagePort session; the preview's HTTP and SSE are still to come). This folder never imports today's renderer, `shared/live`, `AppState` or `engine/*`.

## `api` is the F2 client

Each `api` member is the F2 typed client's method of the same name (`api.<type>.<verb>` for contract method `Type/verb`), and its type is the client's own (`Api` from `@aplos/contract/client`), so the two cannot drift. Three things differ, and only in the data layer's favour: fresh `opId`s and `requestId`s are optional (the data layer mints them), and the two overlay methods (`thread.act`, `operation.undo`) return an `ActResult` synchronously. Reads that have a hook (`View/*`, `T/get`, `Session/get`, `Counts/get`, `Setup/status`) are not on `api`.

`CONTRACT_METHODS` in `index.ts` is the mapping table. Its type rejects a method the registry does not have and checks `native` against the contract's host; the runtime test checks each name against the registry.

A command that returns a receipt but has no overlay (every "operation" row above) goes through one path in `layer.ts`: it mints the `opId` when the caller gives none, records an operation (`OperationView`, kind `command`) so toasts can word it, retains the engine's `Operation` row once the receipt lands, and pushes it on the one undo stack when it is issued, as `api.thread.act` does (it leaves the stack if the receipt says `undoable: false`; Z then calls `Operation/undo`, which marks the operation undone at once; there is no optimistic overlay, the engine's frames update the rows). A refusal takes the same path as `act` and undo: the operation is marked failed and the caller gets an `OperationFailedError` (`opId`, `error`). `OperationView.retry()` sends the write again under a fresh `opId` and yields only `{opId, receipt}`, so after retrying `plan.confirm`, `ask.decide` or `calendar.set` a screen re-reads the rows instead of relying on `eventId`, `draftId` or `calendar` from the first result. No new frame kind: streams already work through `useFrames`.

## Release rule

No release ships before the switch to the real engine (plan 30 4.1, build-order step 2). `renderer/main.tsx` boots the stand-in only in a development build; a production build loads today's renderer. `shell/app.test.ts` re-runs the boot path headless: stand-in, Home window, rendered lines. The `srcdoc` mail frame (`MailFrame.srcdoc`, set by the stand-in only) is a development path, never a shipped fallback (ARCH 10).
