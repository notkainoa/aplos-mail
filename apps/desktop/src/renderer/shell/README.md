# `renderer/shell`: what other lanes call on the shell (F9)

This folder holds the few shell functions that screens owned by other lanes need. It is part of Phase 0 artifact F9 and freezes on day 3 (2026-10-29). After the freeze, changes are **additive only**. Lane `ui-shell` owns the folder. `index.ts` is implemented on small module-level stores (`store-core.ts`, `store-sheet.ts`, `store-target.ts`, `store-toast.ts`, `store-route.ts`); React reads them with `useSyncExternalStore`. `NotImplementedError` stays exported but nothing throws it now.

Run the tests with `cd apps/desktop && npx tsx --test 'src/renderer/shell/*.test.ts'`. `app.test.ts` covers the new renderer entry's boot proof (`renderer/App.tsx`, mounted by `renderer/main.tsx`): it boots the stand-in engine on the `demo` and `empty` scenarios, watches Home through `watchHome` (window frames, `Counts` changes, a `reset` frame reopening the window), and renders `HomeContent` with react-dom/server, in node with no DOM. `npx tsc --noEmit -p apps/desktop/tsconfig.json` checks the call examples and their `@ts-expect-error` lines.

## The surface in plain words

**Sheets.** `ui-onboard` builds the reconnect sheet and the consent card, but other lanes open them: the status slot, Settings → Accounts, Settings → AI and Ask. They call `openSheet('reconnect', {accountId, mode})` with `mode` `'reconnect'` (for `needsReauth`, or `health.reconnectBy` within 24 hours), `'grant'` (for `needsPermission`) or `'enableEditing'` (Settings → Calendar's "Enable editing"). The sheet then calls `api.account.reconnect` or `api.account.grantPermissions` (`'enableEditing'` adds `enable: 'calendarWrite'`) and follows that flow's `connect` frames. For consent they call `openSheet('consent')`, optionally with `{provider, model}` in the contract's names, which otherwise default to the Summaries choice; Allow sends `api.consent.grant`. The shell shows one sheet at a time. Opening a different one cancels the first. While a sheet is open the shell adds the modal `sheet` key context, so nothing behind the sheet answers; the sheet host registers `sheet.cancel` (Esc: `closeSheet()`) and `sheet.default` (Return: Allow for consent, Try again for a failed reconnect, nothing otherwise). A `connect` frame that names another account than the sheet's is ignored, and the sheet closes if its account is removed. `closeSheet()` closes it, and `useSheet()` tells the shell's sheet slot what to render (gap list U5, S16).

**The command target.** The palette's first line names what commands act on ("For: Drew Bell · October illustrations"). The focused screen calls `useCommandTarget({kind, id, title, detail})`. The reader passes its thread, the calendar its open event, Settings the focused account row. The innermost focused caller wins: pass `useCommandTarget(target, {region: ref})` (additive) with the ref of the element the component draws, and the setter whose region is the deepest to contain the focused element wins; without a region, or with focus outside every region, the latest-mounted setter wins. `useCurrentTarget()` returns the target, and the shell puts it in every `CommandContext` (gap list U1, A12).

**Routes.** Choosing a Settings row in ⌘K returns a route such as `settings/mail#undoSeconds`. `openRoute(route)` opens Settings on that section, scrolls the row into view and focuses its control. Ask's "Use another provider" link uses `settings/ai` (gap list U3, S15).

## Additive exports (implementation notes)

- **Add account.** `openAddAccount()` opens the inline Add account dialog (`AddAccountHost.tsx`), the `addAccount` sheet: the onboarding lane's Accounts connect flow (`onboarding/connect.ts`) on the data layer's ports (`renderer/onboardingPorts.ts`) in a Dialog, so one more Google account connects without the setup window. `useAddAccount()` is true while it is open. One sheet at a time (another sheet replaces it and its wait is cancelled), Esc steps back like the onboarding step (cancel the wait, clear the field) and then closes (the rules live in `add-account-controller.ts`, unit-tested without React), focus returns to the opener (`setSheetOpener` for the switcher's menu item). A connect that lands closes it with an "Account added" toast. The switcher's "Add an account" and the no-accounts state's button call it.
- **Window entry.** `renderer/entry.ts` (`chooseEntry`) decides what `main.tsx` boots: in a development build `?window=onboarding&mode=first|review` boots `OnboardingApp` (with `onboarding.css` after `ui/styles.css`), every other window boots `App`; the legacy switch and production builds keep the legacy renderer until WP5.6.

- **Sheet key context.** `renderer/commands` defines the modal `sheet` context and its `sheet.default` / `sheet.cancel` keys but has no helper that pushes it. The shell calls `useSheetContextActive()` and adds `'sheet'` to the contexts it passes to `buildStack`. `registerSheetCancel(hook)` registers a hook called with a sheet that another sheet replaced (the reconnect sheet cancels its `api.account.cancelConnect` flow there); `closeSheet` does not call it. Focus returns to the element focused when the first sheet opened (no DOM, no focus change).
- **Toasts.** An Undo toast is one with `undoable: true` or an action whose `commandId` is `app.undo`. The store runs no timers: the `Toast` component owns the life (plain 4 s, Undo 8 s, `persistent` never, paused on hover and focus) and calls `dismissToast` after its fade (`ToastData.undoable` is set for any Undo toast). `persistent` is how a failure stays (`ToastKind` has no error kind). The stack keeps `TOAST_LIMIT` (3): a fourth drops the oldest toast that is neither Undo nor persistent, which can be the newcomer when three Undo toasts are open; Undo and persistent toasts are never evicted, so the stack can exceed the cap and `ToastStack` shows the last three. A push with a live id updates that toast in place. Done, Later and Trash toasts stack like every other Undo toast and name the sender ("Done · Jordan Park"); Z undoes the newest first. `ToastStack` draws the stack as a deck (newest in front, older ones peeking; hover or focus fans it out and holds every toast's clock). `ToastHost` drops an action's `keysFrom` keycap while the screen under it does not bind that command (R and D belong to Home; the reader's R is Reply), and keeps the button. `holdToast` / `releaseToast` are no-ops kept for the frozen surface. `setToastCommandRunner(run)` is how the shell wires the registry: `runToastAction(id, actionId)` calls `run(commandId)` (`KeysProviders` mounts it over the registry and the current context stack, and clears it on unmount), closes the toast only when the registry says the command ran (a refused or failed Undo keeps it), and otherwise falls back to the toast's `onAction` and then closes. The shell attaches a default `app.undo` handler (`undoStack.undoLast()`) when it creates the registry, so Z and the toast's Undo work on every screen; a screen's own registration shadows it. A push or patch never turns a live Undo toast into a plain one. Navigation, saves and sync ticks never toast: callers do not push for them.
- **Routes.** `openRoute` also shows Settings and leaves the route pending. Settings reads `useSettingsTarget()` (or `useRoute()`), opens `section`, scrolls `row` into view, focuses its control, then calls `consumeRoute(seq)`. `useAppRoute()` / `navigate(screen)` hold the shell's current `Screen` (default `'home'`).

- **Overlay key contexts.** The shell's key listener adds the modal contexts open around the event target and the focused element: an ancestor with `data-keyctx` (comma separated), else a `role="menu"` (`menu`, or `datePicker` inside `.ui-date-presets`), a `role="dialog"` (`dialog`, or `palette` for `.ui-palette__panel`). Letters typed there never reach the list or global commands behind.
- **Accounts loaded.** `useAccountsLoaded()` (data, additive) is true once `Account/get` has answered, so an empty `useAccounts()` means "no accounts" only then. Home shows nothing, not the add-account line, until it is true and the engine is no longer connecting; the shell resets a stale account scope once it is true.

## Known gaps

- The ⌘-held hold tracker is not wired: `holdCommandId` is unused, so holding R or A does not yet upgrade to dictation from the shell.
- A plain notice is dropped when three Undo toasts are open (the stack never evicts an Undo toast, and the plain newcomer is the one that goes).
- `FatalScreen` has no `canRetry` prop, so `FatalHost` cannot hide Restart when the engine says it cannot retry.
- A refused push onto a live Undo toast's id is silent (the Undo stays; the caller gets the id back).
